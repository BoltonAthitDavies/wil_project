## ส่วนที่ 1 — ปัญหาและวัตถุประสงค์ (3:40)

**สไลด์ 1 — Title** [0:15]
สวัสดีครับ โปรเจกต์ของผมคือ vision-based navigation pipeline สำหรับ autonomous mobile robot ในโกดังที่มีการเคลื่อนไหว ผมชื่อ Bolton Athit Davies อาจารย์ที่ปรึกษาคือ Dr. Rattanachai Ramaithitima ครับ

**สไลด์ 2 — ปัญหาของ Gensurv** [0:45]
โปรเจกต์นี้เริ่มจากโกดังของ Gensurv หุ่นที่ใช้กันอยู่ตอนนี้ ไม่ว่าจะเป็น latent mobile robot, tow truck หรือ AGV ที่นำทางด้วย QR code ล้วนต้องพึ่งตัวอาคาร คือ marker บนพื้น QR code หรือ reflector ถ้าเปลี่ยน layout ก็ต้องเปลี่ยนโครงสร้างพวกนี้ตาม ซึ่งมีค่าใช้จ่ายสูง ส่วน 2D LiDAR navigation ไม่ต้องใช้ marker แต่ระบุตำแหน่งได้ยากเมื่อฉากมีของเคลื่อนที่ตลอดเวลาและเมื่อสภาพแวดล้อมเปลี่ยน คำถามของโปรเจกต์จึงคือ กล้องจะมาแทนโครงสร้างพื้นฐานเหล่านี้ได้หรือไม่

**สไลด์ 3 — LiDAR เทียบกับ stereo camera** [0:35]
ตารางนี้คือการแลกกันระหว่างสองแบบ LiDAR วัดความลึกได้โดยตรงและ scale แม่นยำ แต่ตัวที่ดีมีราคาแพง stereo camera ได้ความลึกทางอ้อมจาก disparity จึงต้องคำนวณมากกว่า และจะล้มเหลวในที่ที่ไม่มี texture หรือไม่มีแสง ข้อดีของมันคือราคา กล้องตัวละหลักสิบถึงหลักร้อยดอลลาร์ แทนที่จะเป็นหลักพัน

**สไลด์ 4 — Visual SLAM คืออะไร** [0:15]
Visual SLAM คือการประมาณว่ากล้องอยู่ตรงไหน ไปพร้อมกับการสร้างแผนที่ของบริเวณที่ผ่านมา ทั้งสองอย่างในเวลาเดียวกัน

**สไลด์ 5 — Front end** [0:25]
ระบบแบ่งเป็นสามส่วน ส่วนแรกคือ front end ซึ่งประมาณการเคลื่อนที่จากเฟรมหนึ่งไปอีกเฟรม แบบ feature-based ซึ่งทั้งสองระบบของผมใช้ จะเลือกจุดมุมจำนวนหนึ่งแล้ว match ระหว่างเฟรม ส่วนแบบ direct จะใช้ความสว่างของ pixel โดยตรงแทน

**สไลด์ 6 — Back end** [0:25]
Back end รับค่าการเคลื่อนที่คร่าวๆ จาก front end แล้วทำให้สอดคล้องกันทั้งเส้นทาง แบบ filter ทำทีละ state ต่อเนื่องกันไป ส่วนแบบ optimisation สร้าง graph ของ pose กับ constraint แล้วแก้สมการทั้งก้อน estimator ทั้งสองตัวของผมเป็นแบบ optimisation

**สไลด์ 7 — Mapping** [0:20]
ส่วนที่สามคือแผนที่ sparse map เพียงพอสำหรับการระบุตำแหน่ง แต่ dense map เช่น occupancy grid คือสิ่งที่ระบบนำทางต้องใช้ในการวางแผนเส้นทาง

**สไลด์ 8 — วัตถุประสงค์** [0:40]
โปรเจกต์จึงมีวัตถุประสงค์สี่ข้อ ข้อแรก สร้าง localization and mapping pipeline ที่ใช้แค่กล้องกับ IMU โดยไม่มี marker บนพื้น ข้อสอง ทำให้การระบุตำแหน่งนั้นทนทานในโกดังที่มีรถวิ่ง ข้อสาม สร้าง 2D cost map ให้ระบบนำทางใช้ได้ และข้อสี่ relocalise หุ่นใน prior map เพื่อให้แผนที่ช่วยแก้ drift

## ส่วนที่ 2 — Requirement และ scope (1:45)

**สไลด์ 9 — Requirement** [1:00]
วัตถุประสงค์เหล่านี้กลายเป็น requirement สี่ข้อ ตัว pipeline ประกอบด้วย stereo-inertial front end สองตัว คือ ORB-SLAM3 และ VINS-Fusion โดยมี RTAB-Map เป็น back end ที่สร้าง prior map และ relocalise ในแผนที่นั้น และส่งผลลัพธ์ออกไปในรูปแบบที่ Nav2 ใช้ได้

จากนั้นคือการประเมินสามเรื่อง เรื่องแรก ความแม่นของการระบุตำแหน่งเทียบกับ ground truth ทั้งในโกดังนิ่งและโกดังที่มีรถวิ่ง และเทียบกับ estimator ที่ไม่ใช้กล้องเลย เรื่องที่สอง prior map ซึ่งประเมินสองทาง คือ pose graph และ occupancy grid เรื่องที่สาม การ relocalise ในแผนที่นั้น

ตารางด้านขวาคือเป้าหมายที่กำหนดไว้ก่อนเห็นผล ATE ไม่เกิน 5 เซนติเมตร RPE ต่อวินาทีไม่เกิน 10 เซนติเมตร map precision อย่างน้อย 90 เปอร์เซ็นต์ completeness อย่างน้อย 85 เปอร์เซ็นต์ false obstacle ไม่เกิน 1 เปอร์เซ็นต์ ช่วงเวลาที่ไม่มี fix ไม่เกิน 10 เปอร์เซ็นต์ และไม่มี pose กระโดดเกิน 1 เมตร

**สไลด์ 10 — Scope** [0:45]
ขอบเขตของงาน ฝั่ง simulation ใช้โกดัง Gazebo แบบสมจริงสอง layout มี recording สำหรับการระบุตำแหน่งสี่ชุด recording สำหรับสร้างแผนที่ระยะยาวสองชุด และการ relocalise หกรัน ฝั่งหุ่นจริงคือแพลตฟอร์ม Ackermann ที่ Gensurv ติด fisheye stereo camera กับ IMU 200 Hz มีสี่ recording ที่มี ground truth จาก tracker ทุกอย่างประมวลผลบน laptop เครื่องเดียว คอมพิวเตอร์บนหุ่นทำหน้าที่บันทึกข้อมูลอย่างเดียว ข้อมูลที่บันทึกไว้ถูก replay ที่ความเร็วจริง ส่วนการ relocalise ทำแบบ live ใน simulation โดยขับหุ่นด้วยมือ

**เวลาสะสม: 5:25**

## ส่วนที่ 3 — Literature review (2:45)

**สไลด์ 11 — วิธี VI-SLAM** [0:35]
ทำไมต้อง visual-inertial กล้องอย่างเดียวไม่รู้ scale และพังเมื่อเคลื่อนที่เร็ว IMU อย่างเดียวก็ drift ภายในไม่กี่วินาที เมื่อรวมกันจะปิดจุดอ่อนของกันและกัน งานทบทวนนี้รวบรวมระบบ visual-inertial หลักๆ ในช่วงสิบปีที่ผ่านมา ผมคัดเหลือสองตัวที่รองรับ stereo และ fisheye ยังมีการพัฒนาต่อเนื่อง และรันบน ROS ได้ คือ ORB-SLAM3 และ VINS-Fusion

**สไลด์ 12 — Systems challenges** [0:35]
งานวิจัยนี้วัดคำถามเดียวกันบนฮาร์ดแวร์จริง ด้านซ้ายคือ latency บน laptop ที่ 20 เฟรมต่อวินาที ORB-SLAM3 ใช้ 46 มิลลิวินาทีต่อเฟรม บน Jetson ราว 93 ด้านขวาคือ trajectory error ซึ่งอยู่ในระดับไม่กี่เซนติเมตรทั้งชุดข้อมูลง่ายและยาก ข้อสรุปสำหรับโปรเจกต์นี้คือ บนฮาร์ดแวร์ฝังตัว ความแม่นไม่ใช่คอขวด การคำนวณต่างหากที่เป็น นั่นคือเหตุผลที่ต้นทุนการคำนวณเป็นส่วนหนึ่งของการทดลองที่หนึ่ง

**สไลด์ 13 — ORB-SLAM3** [0:35]
ORB-SLAM3 ทำงานสาม thread Tracking ประมาณ pose ของทุกเฟรมจาก ORB feature และ IMU ที่ preintegrate แล้ว Local mapping ปรับ keyframe ล่าสุดให้ละเอียดขึ้นและ initialise IMU ส่วน Loop closing จดจำสถานที่ที่เคยเห็นแล้วแก้ทั้งเส้นทาง ขอให้จำ loop closer ตัวนี้ไว้ เพราะมันเป็นตัวกำหนดผลส่วนใหญ่

**สไลด์ 14 — VINS-Fusion** [0:30]
VINS-Fusion เป็น estimator แบบ tightly coupled ที่ใช้ optimisation ติดตามจุดมุมด้วย optical flow และแก้ sliding window ของ keyframe ล่าสุดร่วมกับ IMU ส่วน state เก่าจะถูก marginalise ออก เวอร์ชันที่เราใช้ไม่มี loop closure จึงเป็น odometry ล้วน และ error ทำได้แค่สะสมเพิ่มขึ้น

**สไลด์ 15 — RTAB-Map** [0:30]
RTAB-Map เป็น SLAM library แบบ graph คุณสมบัติสำคัญสำหรับโปรเจกต์นี้คือ มันรับ odometry จากภายนอก front end ตัวไหนก็ป้อนให้มันได้ แล้ว RTAB-Map เติมสิ่งที่ front end ไม่มีให้ คือแผนที่ที่บันทึกไว้ การจดจำสถานที่เทียบกับแผนที่นั้น และ occupancy grid สำหรับ Nav2

**เวลาสะสม: 8:10**

## ส่วนที่ 4 — Methodology (2:25)

**สไลด์ 16 — System architecture** [0:40]
นี่คือภาพรวมทั้งระบบ stereo pair กับ IMU ส่งข้อมูลเข้า front end ที่ 30 และ 200 hertz odometry จาก front end ไปที่ RTAB-Map ซึ่งระบุตำแหน่งบน prior map ที่สร้างไว้ล่วงหน้าครั้งเดียว correction ที่ได้จะผ่าน correction gate และ pose gate ก่อนถึง Nav2 ส่วน planning กับ control ทางขวาเป็น Nav2 มาตรฐาน ใช้ planner แบบ Hybrid-A* กับ pure pursuit ซึ่ง planning อยู่นอกขอบเขตของผม งานของผมคือกล่องสีส้มทางซ้าย

**สไลด์ 17 — ORB-SLAM3 กับ RTAB-Map** [0:30]
ภายใน RTAB-Map มีสี่ขั้นตอน สร้าง node ใหม่จาก pose ของ front end กับ stereo pair แล้ว bag-of-words เสนอว่า node นี้น่าจะเป็นสถานที่ไหนที่เก็บไว้ จากนั้น geometric verification ตรวจข้อเสนอนั้น และ graph optimisation เปลี่ยน match ที่ผ่านให้เป็น correction สุดท้ายคือประกอบแผนที่และส่ง correction ผ่าน gate

**สไลด์ 18 — Bag-of-words** [0:20]
ทำไมต้องมี bag-of-words เพราะการตรวจ geometry ของทุก node ช้าเกินไป จึงแปลงภาพแต่ละภาพเป็นชุดของ visual word แล้ว node ที่มี word คล้ายที่สุดจะเป็น candidate หนึ่งเดียว

**สไลด์ 19 — Geometric verification** [0:25]
แต่ word แยกทางเดินสองแถวที่หน้าตาเหมือนกันไม่ออก geometry แยกได้ ถ้าเป็นที่เดียวกันจริง จุดที่ match กันต้องเรียงตรงกันในสามมิติภายใต้การเคลื่อนที่แบบ rigid เดียว ถ้าจุดที่เข้ากันมีน้อยเกินไป candidate นั้นจะถูกปฏิเสธ

**สไลด์ 20 — Correction gate** [0:30]
และ gate คือส่วนที่ผมเพิ่มเข้าไป ในโหมด localisation ผลลัพธ์ของ RTAB-Map คือ correction ของตำแหน่งหุ่น ถ้า correction ผิด หุ่นจะถูกย้ายไปอยู่อีกทางเดินในทันที gate ถามคำถามทางกายภาพว่า หุ่นจะอยู่ห่างจากที่ odometry บอกขนาดนั้นได้จริงไหม เมื่อดูจากระยะที่วิ่งมาตั้งแต่ fix ครั้งล่าสุด ถ้าไม่ได้ correction นั้นจะถูกปฏิเสธ

## ส่วนที่ 5 — การตั้งค่าการทดลอง (1:50)

**สไลด์ 21–22 — Layout U และ I** [0:35]
เพื่อทดสอบระบบ ผมสร้างโกดังสอง layout ตามแนวทางของอุตสาหกรรม freight forwarding แบบ U มี receiving กับ dispatch อยู่ฝั่งเดียวกัน และ storage อยู่รอบด้านหลัง แบบ I เป็นการไหลทางตรง receiving อยู่ปลายหนึ่ง dispatch อยู่อีกปลาย ทั้งสองแบบสร้างจาก script เดียวกัน มีชั้นวาง pallet มี pallet jack วิ่งตามงาน และมีคนเดิน

**สไลด์ 23 — Hardware** [0:40]
สองโดเมนของการทดลอง ใน simulation ใช้ stereo pair แบบ pinhole ที่ 30 hertz calibration แม่นตรง และ ground truth สมบูรณ์ บนหุ่นจริงใช้ fisheye camera Sony IMX390 สองตัว RealSense IMU ที่ 200 hertz extrinsic วัดด้วยตลับเมตร และใช้ optical tracker เป็น ground truth ซึ่งวัดได้แค่ในระนาบ และมีระยะเยื้องของ marker ที่เรายังไม่ได้วัด ขอให้จำจุดสุดท้ายนี้ไว้ตอนดูตัวเลขของหุ่นจริง

**สไลด์ 24 — สองการทดลอง** [0:35]
จึงได้เป็นสองการทดลอง Experiment 1 ถามว่า estimator แต่ละตัวระบุตำแหน่งได้ดีแค่ไหน ทั้งในฉากนิ่งและฉากที่มีรถวิ่ง เทียบกับ baseline ที่ไม่ใช้กล้อง Experiment 2 คือส่วน SLAM สร้าง prior map ตัดสินว่าแผนที่สะท้อนโกดังจริงหรือไม่ และตัดสินว่าหุ่น relocalise ในแผนที่นั้นได้ดีพอที่จะส่ง pose ที่ใช้งานได้ให้ Nav2 หรือไม่

**เวลาสะสม: 12:25**

## ส่วนที่ 6 — Experiment 1 (8:00)

**สไลด์ 25 — ขั้นตอน** [0:30]
Experiment 1 มีสามขั้น เก็บ dataset วัด noise ของเซนเซอร์เทียบกับ ground truth เพื่อให้ estimator ทุกตัวได้ค่า noise ที่ตรงความจริง แล้วสร้างเส้นทางขึ้นใหม่ห้าวิธี คือ ล้ออย่างเดียว IMU อย่างเดียว ล้อกับ IMU รวมกันด้วย Kalman filter VINS-Fusion และ ORB-SLAM3 ตัววัดหลักคือ aligned ATE ซึ่งเป็น RMS error หลังจัดเส้นทางให้ทับกันแบบ rigid ได้ดีที่สุด

**สไลด์ 26 — Dataset ใน simulation** [0:10]
สี่ recording ยาวชุดละ 100 ถึง 170 เมตร คือ U นิ่ง I นิ่ง และสอง layout เดียวกันที่มีรถวิ่ง

**สไลด์ 27 — Estimator ที่ไม่ใช้กล้อง** [0:25]
baseline ทั้งสามตัว wheel odometry อินทิเกรตความเร็วล้อและมุมเลี้ยว IMU dead reckoning อินทิเกรต gyro กับ accelerometer ส่วน EKF ทำนายด้วย IMU แล้วแก้ความเร็วด้วยล้อ

**สไลด์ 28 — Noise** [0:20]

## คำถามที่น่าจะโดนถาม (คำตอบสั้น)

- **ทำไมไม่ใช้แผนที่ของ ORB-SLAM3 เลย?** มันไม่มี occupancy grid ให้ Nav2 และไม่มีทางกัน relocalisation ที่ผิด RTAB-Map รับ odometry จากภายนอกและมีให้ทั้งสองอย่าง (สไลด์ 15, 17)
- **Traffic มีผลต่อการระบุตำแหน่งไหม?** มีผลเฉพาะช่วง error ต่อวินาทีเพิ่มสองถึงแปดเท่าตอนที่มีรถอยู่เต็มภาพ รวมแล้วไม่ถึง 10 เซนติเมตร และไม่ได้กำหนด error โดยรวมที่ความหนาแน่นในการจำลอง อย่าตอบว่า "ไม่มีผล" (สไลด์ 36)
- **ทำไม RPE ผ่าน แต่ ATE 3 มิติไม่ถึง 5 cm?** เพราะการสะสมและความสูง บน I ORB หนึ่งรันได้ 4.4 cm ในระนาบพื้น บน U error ในระนาบเองอยู่ที่ 10–33 cm เป็นการแยกวิเคราะห์หลังเห็นผล อยู่ในตาราง 4.6 ของรายงาน
- **Gate เข้มเกินไปไหม? ปฏิเสธ fix ที่ถูกได้ไหม?** ได้ครับ นั่นคือราคาของมัน ช่วงที่ correction ถูกปฏิเสธ หุ่นวิ่งด้วย odometry อย่างเดียว excursion 6.5 วินาทีครั้งเดียวที่เกิดก็เป็นช่วงแบบนั้น เราแลกการวิ่งด้วย odometry ช่วงสั้นๆ กับการไม่ให้ตำแหน่งกระโดดหลายเมตร
- **ทำไม ATE ของหุ่นจริงไม่นับเป็นการทดสอบตามเป้า?** หุ่นวิ่ง 0.28 m/s แทน 1.5 และระยะเยื้องของ marker บน tracker (0.2–0.4 m ตามแนววิ่ง) ยังไม่ได้วัด
- **เป้า RPE 0.10 m ยุติธรรมไหม ในเมื่อ proposal เขียนไว้ 1.5 m?** เป้านี้ถูกปรับให้เข้มขึ้นหลังเห็นผล และรายงานบันทึกไว้เป็น deviation
