## ส่วนที่ 1 โลก realistic

**หน้า 3 – รูปแบบ flow ของคลังสินค้า**
ก่อนดูโลกที่สร้าง นี่คือสาม layout มาตรฐานจาก reference การออกแบบคลังสินค้า: I-shape ของไหลผ่านจากรับไปส่ง, L-shape, และ U-shape รับกับส่งอยู่ด้านเดียวกัน ผมสร้างสองแบบคือ I กับ U ส่วน L ไม่ได้ทำ

**หน้า 4 – U-shape**
นี่คือ layout แบบ U-shape ที่ generate จาก script ตาม reference การออกแบบคลังสินค้า: receiving กับ dispatch อยู่กำแพงเหนือด้วยกัน
สี่เหลี่ยมสีคือวัตถุ 126 ชิ้นแยกตามโซน เส้นสีคือเส้นทางรถ pallet jack 4 คันที่วิ่งงานวนลูป เส้นประเขียวคือคน 4 คน เส้นเทาคือเส้นทางที่เคยอัดไว้ใน dataset เดิม ซึ่งผมวาง aisle ให้เส้นนี้ยังวิ่งได้

**หน้า 5 – I-shape**
แบบที่สองคือ I-shape: รับของทางเหนือ ส่งของทางใต้ ของไหลผ่านอาคารทางเดียว 121 ชิ้น รถกับคนชุดเดียวกัน
สังเกตเส้นเทา เส้นทางเดิมวิ่งทะลุชั้นวางใน layout นี้ เลยต้องอัดเส้นทางใหม่สำหรับ I-shape

**หน้า 6 – 4 recordings**
อัดมา 4 ชุด: แต่ละ layout มีแบบมีรถวิ่งและแบบ static twin ที่วัตถุเหมือนกันทุกชิ้นแต่ปิด plugin รถ ดูคอลัมน์ Objects จะเห็นว่าคู่เดียวกันมีวัตถุเท่ากัน 125 กับ 119
ข้อจำกัดอยู่ที่คอลัมน์ Route: คู่ U ยาวต่างกัน 68 เมตร เพราะขับมือ เพราะฉะนั้นถ้าเทียบ static กับ traffic บน U จะปน route เข้าไปด้วย

**หน้า 7 – traffic อยู่ในกล้องเมื่อไหร่**
ผมดึงตำแหน่งรถจาก pose stream ใน bag มาคำนวณว่าเวลาไหนรถอยู่ในมุมกล้องจริง ๆ: ภายใน 20 เมตร, ±45 องศา, ไม่มีชั้นวางบัง แถบม่วงคือช่วงนั้น แถบเทาคือช่วงหุ่นเลี้ยว
ค่ากลางคือรถอยู่ในกล้อง 37% ของเวลาที่ track ได้ ส่วนคนเดินไม่มีในแถบนี้เพราะ actor ของ Gazebo ไม่เขียนตำแหน่งลง pose stream

## ส่วนที่ 2 Insight

**หน้า 8 – lever arm**
เรื่องใหญ่สุดที่เจอ: ground truth รายงานตำแหน่ง origin ของโมเดลหุ่น แต่ ORB-SLAM3 กับ VINS รายงานตำแหน่ง IMU ซึ่งอยู่หน้า origin 0.338 เมตรตาม model.sdf และ script ให้คะแนนไม่เคยชดเชย
รูปนี้แต่ละเส้นคือ run หนึ่ง ลองขยับ ground truth ไปข้างหน้าทีละนิดแล้ววัด ATE ใหม่ จะเห็นว่าทุกเส้นต่ำสุดที่เส้นประ 0.338 พอดี มัธยฐาน 0.34 จาก 30 run ทั้งสอง estimator ทั้งสองโลก
ตารางซ้ายล่าง: ATE โลก static ลดจาก 0.32 เหลือ 0.10 สำหรับ VINS, 0.37 เหลือ 0.19 สำหรับ ORB และอาการ "error โตตอนเลี้ยว" ของ ORB ที่ 8.7 มม./วินาที หายไปเป็นศูนย์ มันคือ lever arm ไม่ใช่ estimator
แก้แล้วใน vio_metrics และ regenerate ตารางของ Exp 1 กับ 3 ทั้งหมดแล้ว

**หน้า 9 – EKF vs VSLAM**
หลังแก้ คำตอบคำถามว่า EKF ดีกว่า VSLAM ไหม: นับตัวหนาในตารางบน EKF ชนะ 1 ใน 5 bag, VINS 2, ORB แบบไม่มี loop closure 2
สิ่งที่ EKF มีคือสม่ำเสมอ ต่ำกว่า 0.5 เมตรทุก bag แต่ตารางล่างซึ่งเป็น RPE 1 วินาที EKF แพ้ทุก bag
และความได้เปรียบของ EKF มาจาก calibration: ถ้าให้มันใช้ไฟล์ noise เดียวกับ VSLAM ค่าเฉลี่ยกระโดดจาก 0.33 เป็น 1.14 เมตร แพ้ VINS 5 ใน 5
อีกจุดคือ ATE 3 มิติของ VSLAM ส่วนใหญ่เป็น drift แนวดิ่ง เช่น VINS bag 000 3 มิติ 0.557 แต่ระนาบ 0.115 ซึ่ง EKF แบบระนาบไม่มีทางมี เพราะฉะนั้นต้อง quote ค่าระนาบ

**หน้า 10 – wheel odometry**
error ของ wheel odometry คือ heading error ที่เกิดตอนเลี้ยว ดูแถวล่างเส้นน้ำตาล: heading error กระโดดเป็นขั้นอยู่ในแถบเทาที่เป็นช่วงเลี้ยว แล้วค้างระหว่างแถบ ทั้ง 5 bag
แถวบนคือ error ตามแนววิ่ง ใกล้ศูนย์จนกว่า heading error จะสะสม ระยะทางจากล้อผิดไม่ถึง 1% เส้นเขียวคือ EKF แบนทั้งสามแถว

**หน้า 11 – EKF consistency**
EKF consistent ถึงแค่โค้งแรก เส้นเทาคือ NEES = 3 ค่าที่ถูกต้องสำหรับ 3 DOF เส้นแดงประคือขอบ 97.5% เส้นประดำคือโค้งแรกจาก ground truth
ทั้ง 5 panel เส้นเขียวทะลุขอบตรงเส้นประพอดี ภายใน 0.6 วินาที แล้วไม่กลับลงมาอีก ส่วนเส้นฟ้าที่ใช้ noise ของ VSLAM แม่นน้อยกว่าแต่อยู่ใกล้ขอบกว่า

**หน้า 12 – ORB 6.4 m**
ค่า 6.4 เมตรของ ORB บน bag 003 ที่เคยบอกว่าอธิบายไม่ได้ ตอนนี้อธิบายได้: ซ้าย error อยู่ที่ 2 ถึง 4 เมตร 88 วินาที แล้วเส้นแดงสามเส้นที่ 88 ถึง 90 วินาทีคือ jump 30, 11.6 และ 2.5 เมตร ขวาจุดแดงอยู่ตรงที่เส้นทางปิดลูป
tracking state OK ทุกเฟรม และ run ที่ปิด loop closure ได้ 0.21 เมตร มันคือ loop closure ครั้งเดียวที่ผิด

**หน้า 13 – detector: FP คืออะไร**
Experiment 2: false positive 67 ถึง 74% ไม่ใช่การเห็นผี แต่เป็นกล่องถูกวัตถุแต่ขนาดเล็กเกิน ดู histogram ซ้าย แกนนอนคือ IoU ที่ดีที่สุดของ prediction ที่ไม่ match กับกล่องจริง มวลทางขวาของเส้นประ 0.2 คือ 74 / 67 / 72 / 72% ของแต่ละ bag ส่วนยอดที่ศูนย์ที่ไม่มีอะไรอยู่จริงแค่ 6 ถึง 15%
รูปขวา กล่องพวกนี้อยู่ในแถบแนวนอนแถบเดียวคือระดับชั้นวาง และ 85 ถึง 90% เป็น class box ซึ่งคือ pallet ซ้อน

**หน้า 14 – ขนาดกับ threshold**
ขนาดไม่ใช่สาเหตุ: ซ้าย recall ระดับเฟรมแบนที่ 0.57 ถึง 0.66 ตั้งแต่ 48 พิกเซลขึ้นไป bin เล็กที่ต่ำมีแค่ 121 กล่องจาก 62,282
threshold ก็ไม่ช่วย: ขยับ 0.35 เป็น 0.55 precision ขึ้น 0.67 เป็น 0.75 แต่ recall ลง 0.63 เป็น 0.56 แลกหนึ่งต่อหนึ่ง และ moving recall ในรูปขวาตกตามไปด้วย ส่วน moving กับ static recall ต่างกันไม่เกิน 0.03 ทุก bag

**หน้า 15 – โลก extreme**
Experiment 3 โลก extreme: ทุก run พังตั้งแต่ทางตรงแรก ตารางซ้าย 64 run มี onset ครบ 64 และ 49 run onset ตอนวิ่งตรง ไม่ใช่ตอนเลี้ยว
วัตถุเคลื่อนไหวอยู่ในภาพ 74 ถึง 91% ของเฟรมทั้งหมด เลยแยก "มีวัตถุ/ไม่มีวัตถุ" ใน bag เดียวกันไม่ได้
รูปขวาบน: ORB+YOLO เส้นแดง feature ที่ match ได้ร่วงเหลือราว 20% ก่อน onset 2.5 วินาที คือ mask ดึง feature ออก ส่วน VINS เส้นส้มไม่มี feature ตก มันพังแบบอื่น

**หน้า 16 – โลก realistic: traffic**
โลก realistic: traffic อยู่ในกล้องไม่ได้ทำให้ drift เร็วขึ้น ดูแถว unfiltered: ORB 4 run drift ตอนมีรถ −0.2 ตอนไม่มี 1.5 มม./วินาที มีแค่ 1 ใน 5 run ที่ตอนมีรถสูงกว่า
แถว ORB+YOLO class mask: feature ลดตอนมีรถ 11 ใน 16 run และ drift เร็วขึ้น 7 ใน 10 แปลว่า mask ดึง feature ทิ้งตอนรถผ่าน แต่ n แค่ 1 ถึง 4 run ต่อกลุ่ม นี่คือขอบเขต ไม่ใช่ค่าวัด
และก้าวกระโดดใหญ่อันเดียวของโลกนี้ VINS 002 กระโดด 3 เมตรที่วินาที 29 ถึง 33 เกิดตอนโค้งแรกโดยไม่มีรถในกล้อง กลับไปดู panel ที่สามของหน้า 7 ได้

**หน้า 17 – แผนที่: cell ผิดคืออะไร**
Experiment 4: cell ที่ผิดคือผิวหนาขึ้น ไม่ใช่สิ่งกีดขวางผี ดู legend: เขียว 11,241 ถูก ส้ม 348 หนาเกิน 0.25 ถึง 0.5 เมตรจากผิวจริง แดง 43 เป็นผีเกิน 0.5 เมตร
43 cell แดงรวมเป็น 22 กลุ่ม กลุ่มใหญ่สุดเลข 10, 6, 2 อยู่ที่กำแพงเหนือใต้ ไม่มีใน aisle ที่เส้นทางใช้ สีฟ้า 360 คือผิวจริงที่เห็นแต่ไม่ได้ อยู่บนหน้าชั้นวางฝั่งตะวันออกที่มองเฉียง ๆ จาก aisle

**หน้า 18 – พลาดเพราะมุมมอง ไม่ใช่ระยะ**
ซ้าย precision กับ recall ไม่มีแนวโน้มตามระยะจากเส้นทาง 0 ถึง 6 เมตร ขวา recall 78% ถ้า cell ถูกเห็นจาก node เดียว ขึ้นเป็น 91 ที่สอง node 97 ที่สามถึงสี่ precision 91 ไป 99
มุมตกกระทบก็เหมือนกัน: 95% ที่มองตรง 76% ที่เฉียงเกิน 60 องศา คือ recall gap มาจากเรขาคณิตของเส้นทาง ไม่ใช่ sensor range

**หน้า 19 – ฐานข้อมูลที่ไม่ได้ลงทะเบียน**
เปิดไฟล์ใน map/ ดูทีละอัน: map_tiny สร้างจาก dataset_map_tiny แน่นอน เพราะ node pose ตรงกับ ground truth มัธยฐาน 5 ซม. map_02 เป็นแผนที่ tiny อีกอันคนละเส้นทาง map_03 คือความพยายามทำแผนที่คลังใหญ่ 18 node ความสูงไต่ไป 9.8 เมตร วางลงโลกไหนไม่ได้
สองประโยคใน write-up เดิม "แผนที่ไม่ตรง dataset ไหน" กับ "แผนที่ใหญ่ไม่เหลือไฟล์" ผิดทั้งคู่ ต้องถอน

## ส่วนที่ 3 Motion gate

**หน้า 21 – motion gate ทำงานอย่างไร**
ก่อนดูผล ขอเล่าว่าตัว gate ที่สร้างทำงานยังไง เดินตามกล่องม่วง: กล่องจาก YOLO มาพร้อม timestamp ของภาพ → association จับคู่กับกล่องเฟรมก่อนด้วย IoU และสืบทอดคำตัดสินเดิม → probation ยังไม่ให้โหวตจนกว่าจะตามกล่องนั้นมานานพอและมี keypoint พอ เพราะกล่องที่เพิ่งโผล่กับกล่องที่ขยับดูเหมือนกัน (จุดใหม่ทั้งคู่)
→ census: นับสัดส่วน inlier ต่อ keypoint ในกล่อง เทียบกับสัดส่วนเดียวกันของฉากหลังในเฟรมเดียวกัน ถ้าต่ำกว่า α เท่า (α = 0.25) ตัดสินว่าขยับ กล่องบนบอกว่า "inlier" ใน ORB คือ map point ที่ไม่ถูกตีเป็น outlier หลัง pose optimisation และผูกกับ keyframe แล้ว ใน VINS คือ feature ที่มี depth solve ได้
→ verdict ขยับ/นิ่ง/ไม่รู้ โหวตใหม่ทุก N เฟรมกันคำตัดสินผิดติดถาวร → ทาสีเฉพาะกล่องที่ถูกตัดสินว่าขยับ ขยาย 8 พิกเซล มี safety valve ถ้า mask เกิน 80 % ของภาพให้ทิ้งทั้งแผ่น → mask ไปตัด keypoint ที่ feature extraction ของเฟรมถัดไป
จุดที่อยากให้จำคือลูกศร "read back after tracking": สัญญาณทั้งหมดอ่านกลับมาหลัง tracking เสร็จ

**หน้า 22 – ผล**
motion gate คือ mask กล่องเฉพาะเมื่อ tracker เห็นว่ามันขยับ ผลเป็นลบทั้งสอง pipeline
ตารางซ้าย ORB census บน 3,307 กล่อง-เฟรมที่ขยับจริงและ 1,044 ที่นิ่ง: ที่ threshold 0.25 จับของขยับได้ 82% แต่จับของนิ่งผิดด้วย 76% AUC 0.528 คือโยนเหรียญ ทุกแถวเหมือนกัน
ตารางขวา VINS ลองสามสัญญาณ: solved depth recall 0.25, residual กลับด้านคือของขยับได้คะแนนต่ำกว่า, residual availability 0.56 แต่ false alarm 0.41
สถานะ: implement เสร็จทั้งสอง pipeline ปิดไว้เป็นค่าเริ่มต้น Experiment 3 รายงานด้วย class mode

**หน้า 23 – ทำไม**
สาเหตุเป็นโครงสร้าง ไม่ใช่การจูน: census ทุกตัวอ่านจาก state ที่ estimator ล้างจุดที่ไม่เข้ากับ pose ทิ้งไปแล้ว
ORB นับ map point ที่รอดจาก TrackLocalMap จุดที่ไม่เข้ากับ pose ถูกตีเป็น outlier ไปก่อน เลยเหลือแต่ที่บังเอิญพอดี นั่นคือทำไม recall กับ false alarm เท่ากันทุกแถว
VINS outliersRejection ตัด feature ที่ reprojection เกิน 3 พิกเซลทุกเฟรม feature ของวัตถุขยับหายใน 1 ถึง 2 เฟรม census เลยวัดแต่ตัวรอด นั่นคือทำไม residual ออกมากลับด้าน
การทดลองที่ยืนยัน: ลด min_dist จาก 30 เป็น 15 พิกเซล feature ต่อกล่องเพิ่มสามเท่า แต่สัญญาณหายไปเลย 94.7% ของ feature ในวัตถุขยับมี depth ที่ solve ได้ 0 จาก 83 แถวต่ำกว่า threshold ข้อมูลมากขึ้น สัญญาณไม่มา แปลว่ามันไม่เคยวัดสิ่งที่ต้องการ

**หน้า 24 – flow diagram: gate อ่านตรงไหน หลักฐานหายตรงไหน**
แถวบนคือ front end ของ estimator: เฟรมกล้อง → ดึงและติดตาม feature → ประมาณ pose → กล่องแดงคือ outlier rejection (ORB ใน TrackLocalMap, VINS ใน outliersRejection ที่ตัดเกิน 3 พิกเซล) → เหลือ feature ที่รอด
แถวล่างสีม่วงคือสิ่งที่เราสร้าง: census นับ feature ที่รอดในกรอบของ YOLO แล้วส่ง mask กลับไปเฟรมถัดไป ปัญหาอยู่ที่ลูกศรจากกล่อง "surviving" ลงมา census: มันอ่านหลังกล่องแดง ซึ่ง feature ที่ขัดกับ pose คือหลักฐานของการเคลื่อนที่ถูกลบไปแล้ว census เลยตี 82 % กับ 76 % เท่า ๆ กัน และสุดท้าย mask จริงแค่ 13–16 %
กล่องประด้านบนคือจุดเดียวที่สัญญาณยังอยู่ คือระหว่าง pose กับ rejection ซึ่งยังไม่ได้ลอง

**หน้า 25 – ทางที่อาจได้ผล**
ถ้าจะทำต่อ ต้องเป็นสัญญาณที่คำนวณก่อน rejection: ใน VINS มี rejectWithF ที่เขียนไว้แต่ comment อยู่, predictPtsInNextFrame ที่ไม่เคยถูกเรียก, และ ptsVelocity ที่คำนวณทุกเฟรมอยู่แล้ว ใน ORB คือ reprojection residual เทียบ pose ที่ IMU ทำนาย ก่อนตี outlier
ยังไม่ได้ลองสักอัน และกฎคือห้าม quote ตัวเลขก่อนให้คะแนนกับ ground truth พร้อมระบุขนาดตัวอย่าง เพราะ 19 แถวเคยดูดี 1,044 แถวไม่ดี

### ถ้าถูกถาม

- *ทำไมเพิ่งเจอ lever arm* – เพราะมันไม่โผล่ใน ATE ตัวเดียว เจอตอนทำ within-run contrast ว่า error โตตอนเลี้ยวไหม ซึ่งรูปแบบ "โตตอนเลี้ยว ค้างตอนตรง" เป็นลายเซ็นของ offset แข็งที่หมุนตาม heading
- *การแก้นี้กระทบ real robot ไหม* – ไม่ real robot มี lever arm ของตัวเอง (tracker marker ถึง cam0) ที่ยังไม่ได้วัด และยัง flag provisional อยู่
- *ทำไมโลก extreme ยังมีค่า* – เป็น testbed ของ "พังทันที" ใช้บอกว่า filter ประเมินไม่ได้ในสภาพนั้น ไม่ใช่ testbed ของ drift
- *traffic ไม่มีผลเลยเหรอ* – ไม่มีผลที่วัดได้ด้วย n 2 ถึง 4 run และคนเดินยังไม่ได้นับ เป็นขอบเขตบน ไม่ใช่คำตอบสุดท้าย
