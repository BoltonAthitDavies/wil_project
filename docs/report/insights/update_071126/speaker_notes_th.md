## ส่วนที่ 1 การล็อกชุดข้อมูล

**หน้า 3 – ชุดข้อมูลถูกล็อกเหลือ 11 ชุด**
เรื่องแรกเป็นเรื่องการจัดระเบียบครับ ผมล็อกชุดข้อมูลที่ใช้ทั้งรายงานเหลือ 11 recording ตามตารางนี้ แล้วปลดระวางที่เหลือทั้งหมด ทั้ง campaign `allsensor` เดิม, โลก `nofloortexture`, การรัน relogged เดือนกันยายน, และ real bag รุ่น realv2 ถึง realv5
ผลที่คำนวณจากของเก่าย้ายไป `trash/output/` ทั้งหมด มี log บอกว่าย้ายอะไรไปทำไม ไม่ได้ลบทิ้ง แต่ไม่มีที่ไหนในรายงานอ้างถึงอีกแล้ว
จุดที่เปลี่ยนนิยามสำคัญคือคำว่า dynamic environment: ตอนนี้ถือเป็น *เงื่อนไข* ของ recording ไม่ใช่ factor ที่ทดลอง เพราะไม่มี recording คู่ไหนวิ่งเส้นทางเดียวกัน ถ้าเทียบ static กับ traffic ตรง ๆ จะปน route เข้าไปด้วย

**หน้า 4 – สถานะ 8 ช่องผล**
ตอนนี้ 6 จาก 8 ช่องมีข้อมูลแล้วครับ เทียบกับรอบ 22 ตุลาคมมีสามอย่างที่ขยับ: Experiment 2 จาก untested กลายเป็น completed, Experiment 1 ได้ครึ่งหุ่นจริงเพิ่มมา, และ Experiment 3 ได้ทั้งการวัด cost และได้คำอธิบายว่าทำไม ORB-SLAM3 ถึงพัง
ที่ยังเป็นสีแดงคือ ไม่มี filtered run เลยทั้งสองโดเมน และ VINS ยังไม่มี run ที่ใช้ได้บนหุ่นจริง

## ส่วนที่ 2 Experiment 3: loop closer

**หน้า 5 – 20 run ที่ไม่กรอง**
รันทั้งหมด 20 run ไม่เปิด filter เลย factor คือ estimator, front end CPU กับ GPU, และ loop closer เปิดกับปิด หนึ่ง run ต่อหนึ่งเงื่อนไข
ภาพรวมคือ VINS นิ่งมาก 0.22 ถึง 0.66 เมตร ไม่มี jump เลยสักครั้ง ส่วน ORB-SLAM3 กระจายตั้งแต่ 0.14 ถึง 6.02 เมตร คือ 11 จาก 16 run อยู่ในช่วง 0.14 ถึง 0.52 แล้วอีก 5 run กระเด็นออกไป
ข้อสำคัญคือไม่มี run ไหน track หลุดเลยนะครับ ศูนย์ tracking loss ศูนย์ reset ทั้ง 20 run เพราะฉะนั้นที่กระเด็นไม่ใช่เพราะ track ไม่ติด

**หน้า 6 – ทุกครั้งที่ ORB-SLAM3 พัง คือ loop closer**
นี่คือผลหลักของรอบนี้ครับ ผมไล่ดูทีละ recording แล้วพบว่า error ที่กระเด็นของ ORB-SLAM3 อธิบายได้ด้วย loop closer ทั้งหมด และมันพังได้สองทาง
แถว `realistic_001` คือปิด closer ได้ 0.5 และ 0.4 เมตร แต่พอเปิด closer กลับเป็น 6.02 กับ 4.78 — closer ทำให้แย่ลง
แถว `realistic_003` กลับกัน ปิด closer ได้ 1.76 กับ 1.91 แต่เปิดแล้วได้ 0.14 กับ 0.50 — closer ช่วย
ส่วน U layout สองแถวบน closer แทบไม่ทำอะไรเลย แก้แค่ 7 ถึง 12 เซนติเมตร
ย้ำว่าสถานะ closer อ่านจาก log ของ run เอง ไม่ได้อ่านจากชื่อ run เพราะเคยเจอ run ที่ชื่อว่าเปิดแต่จริง ๆ ปิด

**หน้า 7 – false closure 14 เมตรบน I layout**
มาดูเคสที่ closer ทำพังก่อน บน `realistic_001` ซึ่งเป็น I layout ที่ทางเดินขนานกันหลายแถว
ทั้ง front end CPU และ GPU ยอมรับ closure เดียวกัน ที่เวลาเดียวกันคือ 73.2 วินาที แล้วแก้ตำแหน่ง 14.7 กับ 13.3 เมตร
ที่บอกว่ามันผิดแน่ ๆ เพราะก่อนหน้านั้น estimate เพิ่งเพี้ยนไปประมาณครึ่งเมตรเท่านั้น ไม่มีทางที่การกลับมาที่เดิมจริง ๆ จะต้องแก้ถึง 14 เมตร และ keyframe ที่มันจับคู่กันอยู่ห่างกันแค่ *ทางเดินเดียว*
หลังจากนั้นมีอีก 4 candidate ที่ถูกปฏิเสธด้วย inertial geometry check แต่ปฏิเสธหลังจากพังไปแล้ว
ที่ front end ทั้งสองแบบพังที่เฟรมเดียวกัน แปลว่าปัญหาอยู่ที่ place recognition ไม่ใช่ที่ตัว extractor
ดูกราฟขวามือ เส้นกระโดดขึ้นที่ 73 วินาทีคือจังหวะนั้น

**หน้า 8 – I layout ที่มี traffic กลับต้องพึ่ง closure**
พอมาดู `realistic_003` ซึ่งเป็น I layout เหมือนกันแต่มีรถวิ่ง กลับกลายเป็นว่า run ที่ปิด closer ได้ 1.76 กับ 1.91 เมตร
แต่ถ้าไปดู error บนระนาบพื้น มันไม่เคยเกิน 0.7 เมตรเลยนะครับ ความต่างอยู่ที่แนวดิ่ง: run ที่ปิด closer ลอยขึ้นไป 4.7 กับ 5.1 เมตรเหนือพื้น
run ที่เปิด closer อยู่ในช่วง 1.4 เมตรและได้ 0.14 กับ 0.50
เพราะ ATE ของเราเป็นสามมิติ มันเลยคิดค่าการลอยขึ้นนี้เข้าไปด้วย ทั้งที่หุ่นวิ่งบนพื้นราบ เพราะฉะนั้นเวลาอ่านผลต้องอ่านตาราง onset บนระนาบควบคู่กันเสมอ

**หน้า 9 – GPU front end เปลี่ยนจำนวนเฟรม ไม่ได้เปลี่ยนความแม่น**
เรื่อง GPU front end ที่ทำไปก่อนหน้านี้ ผลสรุปคือมันเปลี่ยนว่าเฟรมรอดกี่เฟรม ไม่ได้เปลี่ยนความแม่นยำ
GPU เก็บเฟรมได้ 97 ถึง 99 เปอร์เซ็นต์ ส่วน CPU ได้ 72 ถึง 94 เวลา tracking 30 ถึง 37 มิลลิวินาที เทียบกับ 49 ถึง 55
แต่พอเทียบความแม่นเป็นคู่ CPU กับ GPU ที่สถานะ closer เดียวกัน 5 จาก 8 คู่ต่างกันไม่เกิน 0.16 เมตร อีก 3 คู่ที่ต่างมากคือแต่ละ run มี event ของตัวเอง และต่างกันคนละทิศ
สรุปคือที่ frame budget ระดับนี้ extractor ไม่ใช่คอขวดของความแม่น

## ส่วนที่ 3 Experiment 3: cost

**หน้า 10 – วัด cost บน mapping run สองชุด**
การวัด latency กับ resource ผมย้ายมาวัดบน mapping run สองชุดเท่านั้น รันชุดละ 3 ครั้ง
เหตุผลคือ recording สั้นสี่ชุดมี run เดียวต่อเงื่อนไข จะรายงานค่าความไม่แน่นอนไม่ได้
และ mapping run ยาว 288 กับ 315 วินาที วิ่งครบทุกทางเดิน แล้วก็เป็น recording เดียวที่วิ่งถึงความเร็วเป้าหมายของโครงงานคือ 1.5 เมตรต่อวินาที ค่ากลางได้ 1.49 กับ 1.48
รวมทั้งหมด 18 run คือ ORB-SLAM3 แบบ CPU และ GPU ปิด closer กับ VINS อย่างละ 3 ครั้ง

**หน้า 11 – ไม่มีฝั่งไหนถูกกว่า เป็นการแลกหน่วยความจำกับ core**
นี่คือผลที่เพิ่งได้เมื่อวานนี้หลังจากพี่รัน VINS เพิ่มให้ครับ
VINS back end ใช้ 44 มิลลิวินาที ส่วน local mapping ของ ORB-SLAM3 ใช้ 211 ถึง 406 คือเร็วกว่า 5 ถึง 9 เท่า และ VINS ใช้หน่วยความจำแค่ประมาณหนึ่งในสี่ คือ 479 ถึง 497 เทียบกับ 1719 ถึง 1816 เมกะไบต์
แต่ VINS ใช้ CPU มากกว่าสองเท่า คือประมาณ 8 core เทียบกับ 3.5 core
front end ของสองฝั่งต่างกันไม่ถึง 6 มิลลิวินาที
เพราะฉะนั้นข้อสรุปคือไม่มีฝั่งไหน "ถูกกว่า" ตรง ๆ มันเป็นการแลกระหว่างหน่วยความจำกับจำนวน core ซึ่งสำคัญมากตอนจะย้ายไปลงบอร์ด Jetson

**หน้า 12 – ผล I layout ปนกับความร้อน**
มีข้อควรระวังหนึ่งข้อครับ บน U recording ผล GPU เป็นไปตามที่เคยเห็น คือ 37 เทียบกับ 42 มิลลิวินาที เก็บเฟรม 96 เทียบกับ 93
แต่บน I recording กลับทิศ กลายเป็น 52 เทียบกับ 44 และเก็บเฟรมแค่ 75 เทียบกับ 91
ปัญหาคือผมรันทีละ configuration เป็นบล็อก GPU 6 run ติดกันตอนสามทุ่มถึงสี่ทุ่ม CPU 6 run ตอนห้าทุ่มถึงเที่ยงคืน แล้ว VINS อีกชุดตอนเที่ยงวันถัดมา บนเครื่องที่ลด clock ตอนร้อนถึง 90 องศา
ตัวที่ช่วยยืนยันคือ VINS ให้ค่าเท่ากันทั้งสอง recording คือ 38.1 กับ 38.6 มิลลิวินาที แปลว่าตัว recording เองไม่ได้ทำให้ต่างกันขนาดนั้น
เพราะฉะนั้นตอนนี้ให้อ้างเฉพาะตัวเลขฝั่ง U ไปก่อน จนกว่าจะรันใหม่แบบสลับ configuration จากเครื่องเย็น

## ส่วนที่ 4 Experiment 1: baseline บนหุ่นจริง

**หน้า 13 – ในซิม EKF แพ้ VINS เมื่อใช้ noise model เดียวกัน**
ฝั่งซิมมีการตัดสินใจเชิงออกแบบหนึ่งข้อ: ตอนนี้ EKF ที่เป็น baseline รันด้วยค่า inertial noise ที่ไฟล์ config ของ *ฝั่งกล้อง* ประกาศไว้ ไม่ได้ใช้ค่าที่วัดเองจาก bag
เหตุผลคือถ้าจะเทียบความแม่นกันตรง ๆ สองฝั่งต้องใช้ noise model ชุดเดียวกันก่อน ไม่งั้นเป็นการเทียบการ tune ไม่ใช่เทียบ architecture
ผลคือที่ค่านั้น EKF ได้ 0.68 ถึง 2.80 เมตร แพ้ VINS ที่ได้ 0.22 ถึง 0.66 ทั้งสี่ recording
แต่ถ้าให้ EKF ใช้ค่าที่วัดเอง มันได้ 0.21 ถึง 0.58 และจะชนะ VINS สามจากสี่
สรุปคือช่องว่างทั้งหมดอยู่ที่ noise model ไม่ได้อยู่ที่ architecture และค่า gyroscope ที่ config ประกาศไว้สูงกว่าที่วัดได้จริง 5 ถึง 7 เท่า

**หน้า 14 – หุ่นจริงมี baseline แล้ว และกล้องไม่ชนะ**
อันนี้เป็นของใหม่ทั้งหมดครับ พี่ถามว่าทำ scale เองได้ไหม คำตอบคือได้
ข้อจำกัดคือหุ่นจริงไม่ส่ง wheel speed เป็นหน่วยเมตร ไม่มี joint state และ feedback พวงมาลัยเป็นแค่ echo ของคำสั่งที่มีสองค่า เพราะฉะนั้นทำ bicycle model ไม่ได้ ทำ EKF ไม่ได้
สิ่งที่ทำได้คือ เอา speed feedback คูณ scale ตัวเดียว แล้วเอาทิศทางจาก gyroscope ที่หัก bias ตอนอยู่นิ่งออกแล้ว
scale ตัวนี้ รวมทั้ง *แกน* ของ gyro และเครื่องหมาย ผม fit บน `realv7_000` ชุดเดียว แล้วตรึงค่าไปใช้กับชุดที่เหลือ
เรื่องแกนสำคัญมาก: yaw rate ของเซนเซอร์ตัวนี้อยู่บนแกน y ไม่ใช่ z แกน z อินทิเกรตแล้วได้เกือบศูนย์ทั้งที่หุ่นหมุนไป 6.3 เรเดียน ตอนแรกผม fit ด้วยแกน z แล้วพังเลย
ผลคือ wheel+gyro ได้ 0.26 กับ 0.22 เมตรบนสองชุดที่ตรึงค่า ส่วน ORB-SLAM3 ที่ดีที่สุดได้ 0.44 กับ 0.47 คือ baseline ชนะ ส่วน realv6 เสมอกันที่ 0.46

**หน้า 15 – ข้อจำกัดของการเทียบนี้**
ต้องพูดข้อจำกัดให้ชัดครับ ตัว scale นี้ fit กับ tracker ตัวเดียวกับที่เอาไปให้คะแนน แค่คนละ recording เพราะฉะนั้น 0.06 เมตรบนชุดที่ fit ถือเป็นการ calibrate ไม่ใช่ผล
ที่พอยืนยันได้บ้างคือค่า k ที่ fit ได้คือ 0.325 ตรงกับอัตราส่วนความยาวเส้นทางของ realv7 ทั้งสามชุดคือ 0.323 ถึง 0.329
อีกอย่างที่ดูดีคือ path ratio ออกมาใกล้ 1 ภายใน 4 เปอร์เซ็นต์ ขณะที่ฝั่งกล้องวิ่งเกินจริง 5 ถึง 15 เปอร์เซ็นต์
ข้อควรระวังคือเส้นทางแค่ 22 ถึง 37 เมตรที่ความเร็ว 0.2 เมตรต่อวินาที ถ้าเส้นทางยาวกว่านี้ gyro จะ drift มากขึ้นเรื่อย ๆ แต่ฝั่งกล้องไม่จำเป็นต้องแย่ลงตาม
ทางแก้คือวัด scale จริงจากเส้นรอบวงล้อกับอัตราทด และบันทึกมุมพวงมาลัยเป็น measurement ซึ่งจะได้ EKF กลับมาด้วยโดยใช้ wheelbase 0.60 เมตรที่พี่ให้มา

## ส่วนที่ 5 Experiment 2: detector

**หน้า 16 – checkpoint 4 class ทำให้ pallet jack วัดได้**
Experiment 2 กลับมาวัดได้แล้วครับ ด้วย checkpoint 4 class ที่พี่บอก เพราะ class ที่สี่คือ forklift มันจับ pallet jack ซึ่งเป็นวัตถุที่เคลื่อนที่จริงในโลก realistic
วัดบนทั้งสี่ recording รวม 12,698 เฟรม ได้ precision 0.747 และ class F1 0.994 เมื่อ localize ถูกแล้ว
recall รายงานสองฐาน: 0.502 เมื่อนับเฉพาะกล่องที่ไม่ถูกยกเว้น และ 0.288 เมื่อนับทุกกล่องที่อยู่ในภาพ
ตัวเลขที่สำคัญที่สุดคือ moving-object recall 0.288 เพราะนี่คือเพดานของประโยชน์ที่ filter จะได้ ถ้า detector เจอวัตถุที่เคลื่อนที่ไม่ถึงหนึ่งในสาม filter ก็ทำได้ไม่เกินนั้น
ข้อจำกัดที่ต้องพูดคือคนเดินเป็น actor ของ Gazebo ไม่มี pose ไม่มี mesh และไม่อยู่ใน class set เพราะฉะนั้นทั้งวัดไม่ได้และ mask ไม่ได้

**หน้า 17 – ที่พลาดคือเรื่องขนาด ที่เกินคือพลาดนิดเดียว**
ดูที่สาเหตุครับ recall เพิ่มขึ้นตามขนาดกล่องอย่างชัดเจน จาก 0.02 ที่กล่อง 24 ถึง 32 พิกเซล ไปถึง 0.64 ที่เกิน 192 พิกเซล
และ pallet jack ที่เคลื่อนที่อยู่บนเส้นโค้งเดียวกับของที่จอดนิ่ง แปลว่า 0.29 เป็นผลของระยะห่าง ไม่ใช่ผลของการเคลื่อนที่
ส่วน false positive 74 ถึง 79 เปอร์เซ็นต์คือทายถูกวัตถุแต่กรอบเหลื่อมไม่ถึงเกณฑ์ IoU มีแค่ 8 ถึง 9 เปอร์เซ็นต์ที่ทายลงบนที่ว่างจริง ๆ
ซึ่งสำหรับ filter ที่ mask เป็นกล่อง ความต่างตรงนี้แทบไม่มีผล

## ส่วนที่ 6 Experiment 4: แผนที่

**หน้า 18 – แผนที่ realistic ทั้งสี่ชุดไม่ผ่านเกณฑ์**
แผนที่ของโลก realistic สี่ชุด คือสองโครงแบบ build คูณสอง layout ไม่ผ่านเกณฑ์ที่ตั้งไว้ก่อนวัดทั้งหมด
เกณฑ์คือ precision อย่างน้อย 90 recall ที่เห็นอย่างน้อย 85 และสิ่งกีดขวางปลอมไม่เกิน 1 เปอร์เซ็นต์
ที่ได้จริงคือ precision 77.8 ถึง 84.8, recall 74.9 ถึง 82.5 และสิ่งกีดขวางปลอม 3.84 ถึง 10.19 เปอร์เซ็นต์
ทุกชุดวัดด้วย recording ที่ไม่ได้ใช้สร้างแผนที่นั้น เพราะถ้าวัดด้วย recording ที่สร้างมันเอง เส้นทางนั้นย่อมวิ่งได้อยู่แล้วโดยปริยาย

**หน้า 19 – โครงแบบเดือนพฤศจิกายนแย่ลงจากสามพารามิเตอร์**
build ชุดพฤศจิกายนแย่กว่าชุดตุลาคม และต่างกันแค่สามพารามิเตอร์ ซึ่งแต่ละตัวทิ้งร่องรอยคนละแบบ
detection rate ต่ำลงทำให้ node น้อยลงและแต่ละ cell ถูกมองเห็นน้อยครั้งลง
grid range ไกลขึ้นทำให้เกิด cell ปลอมตามกำแพงฝั่งตะวันตก
และ ground height ที่ตัดสูงขึ้นทำให้เกิดสิ่งกีดขวางกลางทางเดิน ซึ่งบน I layout เห็นชัดสุดคือ phantom ที่ขวางทางโผล่กลางเส้นทาง ไม่ใช่ตอนเริ่ม
เรื่องสำคัญคือสิ่งกีดขวางปลอมพวกนี้ *ไม่ใช่* ชั้นวางที่หนาเกิน แต่เป็น cell ที่ถูกวางตอน IMU กำลัง initialise ที่จุด spawn บวกกับแถบกำแพงที่เลื่อนไปประมาณครึ่งเมตร
ทางแก้ที่ข้อมูลชี้คือ ทิ้ง cell ของ node แรก ๆ ไป หรือเริ่มทำแผนที่หลังจาก transient นิ่งแล้ว
ข้อจำกัดคือสามพารามิเตอร์เปลี่ยนพร้อมกัน เลยยังบอกไม่ได้ว่าตัวไหนมีผลมากสุด

## ส่วนที่ 7 สถานะรายงานและงานที่เหลือ

**หน้า 20 – รายงานถูกเขียนใหม่บนชุดข้อมูลที่ล็อกแล้ว**
บทที่ 3 ถูกล้างของเก่าออกหมดครับ fragment เก่าเก้าชิ้นถูกถอดออกจากรายงานแล้วเขียนใหม่จากการวัดบนชุดข้อมูลปัจจุบัน ทั้ง registry, โลกจำลอง, ความสมจริงของเซนเซอร์, วิธีของทั้งสี่ experiment, ตารางสถานะ และ rig จริง
ทุกตัวเลขในนั้นวัดใหม่หมด เช่น การลื่นของล้อต่ำกว่า 0.4 เปอร์เซ็นต์ และ noise ของ gyro ต่ำกว่าค่าที่ config ไว้ 5 ถึง 7 เท่า
บทที่ 4 ช่อง 1 ถึง 3 ตอนนี้ generate จาก insight note ด้วยสคริปต์ เพราะฉะนั้นถ้าจะแก้ ให้แก้ที่ note แล้ว regenerate
บทที่ 5 เขียนใหม่ทั้งบท ตอนนี้ 129 หน้า ไม่มี reference ที่หาไม่เจอ

**หน้า 21 – งานที่เหลือ เรียงตามลำดับที่ควรทำ**
เรียงตามลำดับที่ผมคิดว่าควรทำครับ
หนึ่ง ให้ Experiment 3 ได้ทดสอบจริง คือรัน filtered กับ unfiltered บน `realistic_002` และ `_003` จับคู่ตามเกณฑ์ และบน I layout ต้อง *ปิด* closer ไม่งั้น false closure จะกลบผลของ filter ทั้งสองฝั่ง
สอง ใส่ขอบเขตให้ loop closer คือห้ามแก้เกินกว่าที่ IMU จะ drift ได้ แล้วทดสอบบน `realistic_001` ซึ่งทำซ้ำได้แน่นอนทั้งสอง front end
สาม รัน cost ใหม่แบบสลับ configuration จากเครื่องเย็น
สี่ ฝั่งหุ่นจริง ลองเปิด switch initialisation ของ fork, รัน VINS ใหม่ด้วย gravity ที่แก้แล้ว, วัด lever arm, วัด scale ของล้อ
ห้า detector ต้องมี class คนหรือมี annotation มือ ไม่งั้นวัตถุที่ filter มีไว้จัดการยังวัดไม่ได้
หก แผนที่ เริ่มทำหลัง transient และทบทวนพารามิเตอร์ชุดพฤศจิกายน

**หน้า 22 – สรุป**
สรุปหกข้อครับ
รายงานสร้างจาก 11 recording เท่านั้น ของที่ปลดระวางมี log ไม่ได้ลบ
error ของ ORB-SLAM3 ในซิมคือ loop closer และพังได้สองทาง ส่วน front end เปลี่ยนจำนวนเฟรม ไม่ได้เปลี่ยนความแม่น
VINS นิ่งกว่าในซิมและใช้หน่วยความจำหนึ่งในสี่แลกกับ core สองเท่า แต่ยังไม่มี run ที่ใช้ได้บนหุ่นจริง
กล้องยังไม่ชนะ dead reckoning ทั้งสองโดเมน บนเส้นทางความยาวระดับนี้
detector เจอวัตถุเคลื่อนที่ไม่ถึงหนึ่งในสาม ซึ่งเป็นเพดานของ filter ก่อนจะได้ทดสอบเสียอีก
และแผนที่ realistic ไม่ผ่านเกณฑ์ทั้งสี่ชุด โดยสาเหตุคือ transient ตอน initialise ไม่ใช่ชั้นวาง
