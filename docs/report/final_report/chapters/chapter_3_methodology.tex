\chapter[METHODOLOGY]{Methodology}
\label{chap:methodology}

To let the system solve the problem set out in \cref{chap:introduction} and be
deployed on an edge AI computer, this project integrates a neural object
detector (YOLO26) into the core of a visual SLAM framework, a combination
referred to as semantic visual SLAM. This chapter describes the problem and its
scope, the system architecture, the two navigation pipelines as they were
actually built, the simulation and real platforms, the four experiments that
structure the evaluation, the metrics, and the points at which the implemented
system departs from the method originally proposed.

\textbf{Reporting cutoff.} Every implementation claim in this chapter describes
the repository at 7 November 2026. Components are labelled
\status{implemented}, \status{partial}, \status{blocked} or \status{planned};
nothing planned is described in the present tense as though it existed.

\section{Problem, Requirements and Scope}
\label{sec:problem-scope}

The engineering problem is to localize a warehouse AMR with cameras and an IMU,
without floor infrastructure, in an environment whose contents move. The
company's present LiDAR-and-QR-code navigation is accurate but expensive to
install and inflexible (\cref{sec:background}); a camera-based replacement is
attractive only if it stays accurate when goods, pallets and people move
through the field of view, which is exactly the case standard visual SLAM
assumes away.

\textbf{Performance targets.} The project states two trajectory targets for the
integrated system at the robot's working speed of \SI{1.5}{\metre\per\second}:
an absolute trajectory error of at most \SI{0.05}{\metre}, and a relative pose
error over \SI{1}{\second} of at most \SI{1.5}{\metre}. The original objective
list (\cref{sec:objectives}) states the localization requirement as an error
below \SI{10}{\centi\metre} under differing illumination. Both figures are
carried into \cref{chap:results} and every trajectory result is read against
them.

\textbf{Site.} The real tests take place on the first floor of the Gensurv
building, in a mock warehouse of roughly \SI{10}{\metre} by \SI{7}{\metre}
divided into two operating zones, Zone~A and Zone~B, each about
\SI{3}{\metre} square and joined by a walkway (\cref{fig:test-field}). The
walkway carries a \SI{5}{\degree} slope. Goods are \SI{0.3}{\metre} cubes in
stacks whose positions are changed between runs, and a light-control fixture
sets the illumination to a schedule. A motion-capture system provides the
ground-truth reference (\cref{sec:real-site}).

\textbf{Two domains.} Every experiment is defined once and run twice, in a
Gazebo simulation of the warehouse and on the real robot. The simulation
supplies exact ground truth, exact calibration and repeatable dynamic scenes;
the real robot supplies the sensors, the lighting and the physics the project
is ultimately about. The two domains are never pooled.

\textbf{What is excluded.} Path planning and motion control are outside the
project: the pipeline delivers a pose and a map to an existing planner and
controller (\cref{fig:scope-architecture}). Of the five original objectives,
this report addresses objectives~1, 3 and~5 (visual-inertial localization with
mapping, dynamic-object detection, and the integrated localization
requirement). Objective~2 (EnlightenGAN low-light enhancement) and objective~4
(PolyNET lane detection with PID lane tracking) were not pursued within the
reporting period and are recorded as deviations in \cref{sec:deviations}.

\subsection{Semantic visual SLAM data flow}

The architecture is organised in two parts, front-end sensor processing and
back-end SLAM and mapping.

\begin{itemize}[leftmargin=2em]
  \item \textbf{Front-end processing pipeline.}
    \emph{Sensor data ingestion} receives raw images from the wide-angle stereo
    cameras (Sony IMX390, \SI{186}{\degree} field of view) together with
    acceleration and angular rate from the IMU, through ROS~2 nodes. The
    \emph{dynamic object detection module} passes each image to the YOLO26
    model to detect, in real time, movable warehouse objects (goods, pallets,
    people) and emits their bounding boxes. The \emph{dynamic feature masking
    protocol} compares those boxes with the geometric keypoints extracted by
    the SLAM front end (ORB or FAST corners); any keypoint that falls inside a
    dynamic object's box is masked and discarded, so that only features of the
    permanent warehouse structure remain.
  \item \textbf{Back-end SLAM and mapping.} The filtered features enter
    odometry and graph optimisation to estimate the 6-DoF robot state, update
    the 3-D point map of the permanent structure, and build the 2-D occupancy
    grid the navigation system consumes.
\end{itemize}

\subsection{The two navigation pipelines compared}
\label{sec:pipelines-compared}

The project compares two pipeline architectures built on that front end.

\textbf{Pipeline~1: YOLO26 + ORB-SLAM3 (Atlas multi-map system).} A
tightly-coupled visual-inertial SLAM that performs both odometry and map
construction through one graph. Lifelong mapping relies on ORB-SLAM3's Atlas
framework: when tracking is lost because the environment changed, the system
opens a new active map and keeps the old one as non-active; when the robot
returns to a known area the maps are merged and joined by loop closure across
maps. Its strength is high accuracy from tight image--IMU fusion, suited to
areas with clear geometric features (\cref{fig:pipeline1}).

\textbf{Pipeline~2: YOLO26 + VINS + RTAB-Map (decoupled VIO and memory
management).} A decoupled architecture that separates high-rate front-end
odometry from long-term back-end memory management. The front end runs VINS
sliding-window visual-inertial odometry on the static features from YOLO26,
giving low-latency odometry that remains stable when the robot vibrates or
drives the \SI{5}{\degree} slope. Lifelong mapping is handled by RTAB-Map, which
holds its working memory at a constant size to bound computation time and moves
old nodes to long-term memory on disk. Its strength is stable use of hardware
resources: it prevents RAM exhaustion on a small processing board during long
continuous operation (\cref{fig:pipeline2}).

\section{The Pipelines as Implemented}

\subsection{Dynamic feature masking}
\label{sec:masking-formal}

In a dynamic warehouse a conventional SLAM algorithm accumulates drift if it
uses features on moving objects to compute distance. The project therefore
designs a shared front end in which the detector's output filters the geometric
features before they reach the back end. When the stereo camera delivers frame
$I_t$ at time $t$, the image is passed to the YOLO26 network, which returns a
set of bounding boxes
\begin{equation}
  \mathcal{B} = \{B_1, B_2, \ldots, B_K\}, \qquad
  B_k = \{x_k, y_k, w_k, h_k, c_k, P_k\},
  \label{eq:boxes}
\end{equation}
where $(x_k,y_k)$ is the box centre, $(w_k,h_k)$ its width and height, $c_k$
the class label and $P_k$ the confidence. Boxes with $P_k < \tau_{\mathrm{conf}}$
are rejected to limit false positives. Meanwhile the SLAM tracking thread
extracts the frame's feature set $\mathcal{F} = \{f_1,\ldots,f_N\}$ with
$f_i = (u_i, v_i)$. A feature is labelled dynamic when
\begin{equation}
  \exists\, B_k \in \mathcal{B}:\;
  \Bigl(x_k - \tfrac{w_k}{2} \le u_i \le x_k + \tfrac{w_k}{2}\Bigr) \wedge
  \Bigl(y_k - \tfrac{h_k}{2} \le v_i \le y_k + \tfrac{h_k}{2}\Bigr),
  \label{eq:mask-test}
\end{equation}
and is removed immediately, leaving the static feature set
\begin{equation}
  \mathcal{F}_{\mathrm{static}} = \{\, f_i \in \mathcal{F} \mid f_i \notin B_k\ \forall k \,\},
  \label{eq:static-set}
\end{equation}
which is passed to feature matching and re-projection-error minimisation. The
following subsections state where in each estimator that test is actually
applied, because the two front ends re-use features differently and a single
insertion point is not sufficient for both.

\subsection{Navigation and relocalisation integration: the
\repo{vslam_navigation} package}
\label{sec:nav-integration}

The bring-up of the three components above is collected into one ROS~2 package,
\repo{vslam_navigation}, the instrument used to answer the second half of
Experiment~4's question: whether the reconstructed map is usable by a route
planner. The two front ends and the mapping back end are separate processes with
different frame conventions, different image transports and, on the real rig, a
different camera model; operating them by hand produced several invalid runs.
Path planning remains outside the scope of this project (\cref{sec:scope}): the
planner appears only as the consumer that makes the map's usability measurable,
and no navigation result is reported in \cref{chap:results}.

\subsubsection{Pose by transform rather than by topic}

The back end is not told which front end produced its pose. RTAB-Map is given an
\texttt{odom\_frame\_id} and reads the sensor pose from the transform tree rather
than from an odometry message, logging \texttt{subscribe\_odom = false}
accordingly. One back-end configuration therefore accepts ORB-SLAM3 or
VINS-Fusion unchanged. Each front end is told which frame names to broadcast,
which avoids bridging three naming conventions with static identity transforms.
The resulting chain has exactly one publisher per edge in both domains
(\cref{sec:frames-contract}).

\subsubsection{Manufacturing the stereo input}

RTAB-Map's stereo pipeline requires a rectified image pair, both camera
information messages and a static transform to the optical frames, and the
recordings carry only compressed images. \repo{vslam_navigation/scripts/rtab_camera_shim.py}
constructs the missing inputs from the same calibration files the estimators
read, so a single calibration remains the source of truth. The two domains need
different treatment:

\begin{itemize}
  \item \textbf{Simulation.} A Gazebo camera is an ideal pinhole: every
    distortion coefficient is zero and the two cameras share intrinsics, so the
    raw frames already satisfy what rectification would produce and are
    republished unaltered. This shortcut is valid only in simulation.
  \item \textbf{Real rig.} The cameras are approximately \SI{180}{\degree}
    Kannala--Brandt fisheyes (\cref{sec:real-calibration}), and RTAB-Map's
    stereo path has no equidistant model. Every pair is therefore remapped onto
    a virtual rectified pinhole pair of stated horizontal field of view. The
    rectification rotations come from \texttt{cv2.fisheye.stereoRectify}, but
    the projection matrices are constructed explicitly, because OpenCV's own
    projection degenerates towards zero focal length for a lens of this field of
    view. The remap is validated on-line by an epipolar statistic: the fraction
    of cross-checked ORB matches whose rectified rows agree to within two pixels
    at positive disparity.
\end{itemize}

\subsubsection{Three memory modes, and why a prior must be built without
closures}

The back end is operated in one of three modes: \emph{construct} writes a new
database, \emph{extend} appends a session to an existing one, and
\emph{localize} runs read-only against a prior with RTAB-Map's incremental
memory disabled. Priors from the two mapping recordings are built
\emph{closure-free}: both detectors that can add a non-neighbour link are shut,
the appearance-based one by raising its acceptance threshold beyond reach and
the proximity one by disabling it. The reason is measured: on those recordings
the accepted closures were false, and displaced an otherwise \SI{0.15}{\metre}
map by several metres (\cref{sec:map-eval-method}). Visual words are still extracted, so the database
remains usable for localisation; the cheaper alternative of disabling feature
extraction would yield a database that can never relocalise.

RTAB-Map restores its parameter set \emph{from the database}, so a closure-free
prior returns with both detectors still disabled even when the launch requests
closures. Relocalising against a prior \emph{is} the acceptance of a loop
closure against it, so in localize mode the effect is fatal and silent: the node
starts, publishes a localisation pose, and never localises. The symptom is a
covariance trace pinned at RTAB-Map's no-information value of
\num{3e4}, against roughly \num{0.02} for a successful fix. The launch now
sets both parameters explicitly, since a run-time parameter overrides the stored
one. Every localisation run made against a closure-free prior before
6~November~2026 is void and is excluded from this report.

\subsubsection{Gating the planner on the localisation}

A supervisor, \repo{vslam_navigation/scripts/pose_gate.py}, holds the planner's
lifecycle nodes inactive until three conditions hold together: an initialisation
interval has elapsed, the correction between the map and odometry frames has
moved less than a stated step over a number of consecutive samples, and the pose
lies inside the prior graph's node bounds plus a margin. The gate exists because
nothing in the localisation path reports its own failure, and a planner acting
on a wrong pose is worse than one that does not act. It activates the stack
through the lifecycle manager and pauses it again if the conditions stop
holding. The same boolean is consumed by the
command interface, so a lost localisation zeroes the robot's commands rather
than merely stopping replanning.

\subsubsection{Planner, controller and vehicle model}
\label{sec:nav-algorithms}

The planning layer is Nav2~\cite{macenski2020} with three components chosen for a
car rather than for a differential-drive robot: a kinematic search planner, a
pursuit controller, and a velocity smoother that preserves path curvature. None
is a contribution of this project; the configuration is reported because it
decides whether a plan on the reconstructed map is one the vehicle can follow.

One constraint governs every value in \cref{tab:nav-params}. A car cannot turn
on the spot, so for a kinematic bicycle of wheel base $L$ at steering angle
$\delta$ the rear axle traces a circle of curvature
\begin{equation}
  \kappa = \frac{\tan \delta}{L},
  \qquad
  \kappa_{\max} = \frac{\tan \delta_{\max}}{L},
  \label{eq:curvature-bound}
\end{equation}
and the bound is independent of speed. The planned frame is not the rear axle,
however, so the radius that the planner must respect is the larger
$R_b = \sqrt{R^2 + d^2}$, with $R = 1/\kappa_{\max}$ and $d$ the longitudinal
offset of \texttt{base\_link} from the rear axle. Confusing the two radii
produces plans the controller cannot track, and the steering plugin does not
reject an infeasible command: it clamps the radius internally and the vehicle
silently under-turns.

The planner is the Hybrid-A* variant distributed with Nav2, which searches the
vehicle's kinematic state space rather than a grid of free cells and then
refines the result~\cite{dolgov2010}. Its motion primitives are Dubins
curves~\cite{dubins1957}, so every expansion is a path the vehicle could drive,
and the search is forward-only. Reverse primitives are available but not
enabled: the rig carries a forward-facing stereo pair, so reversing would move
the robot in the one direction its sensors do not observe. The planner's
minimum turning radius is set above the kinematic floor rather than at it,
leaving the controller authority to correct tracking error; planning at the
exact limit makes any lateral error unrecoverable.

The controller is Regulated Pure Pursuit~\cite{macenski2023rpp}, which bounds
the commanded curvature geometrically rather than by tuning. It steers towards a
carrot at lookahead distance $L_d$, emitting
\begin{equation}
  \kappa = \frac{2y}{L_d^{\,2}}, \qquad |y| \le L_d
  \quad\Longrightarrow\quad
  |\kappa| \le \frac{2}{L_d},
  \label{eq:rpp-curvature}
\end{equation}
so a lookahead of at least $2R_b$ guarantees that no command exceeds what the
vehicle can steer. That is why the lookahead distances in
\cref{tab:nav-params} are long, and why shortening them to tighten cornering is
counterproductive: it raises the curvature the controller may ask for.
Rotate-to-heading is disabled because it commands a yaw rate at zero speed,
which the bicycle model turns into full steering lock at a standstill. The
velocity smoother scales all velocity components by one factor, so reducing
speed leaves $\kappa = \omega_z/v_x$ and therefore the demanded steering angle
unchanged.

Both costmaps carry the prior map and an inflation layer, and no live obstacle
layer in either domain. The simulated rig has no lidar and the real one has none
either, and the back end's local occupancy grids are disabled in localize mode
because the dense stereo cost starved the front end. Anything that moved into
the environment after the map was built is therefore invisible to the planner,
which is a limitation of the instrument and not a property of the map
(\cref{sec:map-eval-method}).

\subsubsection{Command interface}

The two domains differ structurally, not by tuning. The simulated robot's
steering plugin consumes a velocity command directly, so the planner's output
reaches it unchanged. The real rig accepts a speed and a steering angle on
separate topics, so \repo{vslam_navigation/scripts/ackermann_bridge.py} inverts
the bicycle model,
\begin{equation}
  \delta = \arctan\!\left(\frac{L\,\omega_z}{v_x}\right),
  \qquad |\delta| \le \delta_{\max},
  \label{eq:bicycle-inverse}
\end{equation}
with $L$ the wheel base and $\delta_{\max}$ the steering limit. Three
behaviours in that node are consequences of the platform rather than choices.
The standstill case of
\cref{sec:nav-algorithms} is guarded a second time here: steering is forced to
zero below a speed threshold.
Both outputs are zeroed when no command has arrived within a timeout, so that a
planner crash mid-goal cannot leave the last command executing. The published
speed is also capped in the robot's own command units, which are not
metres per second and whose scale is known only at a single operating point
(\flag{the speed scale is provisional; \cref{sec:real-platform}}).

\subsection{Simulation fidelity and its limits}
\label{sec:sim-fidelity}
Every simulation result in this report rests on how faithfully the simulator
reproduces the sensors and the contact physics. This subsection states what is
modelled, what is idealised, and in which direction each idealisation biases the
comparison between the visual and proprioceptive estimators.

\paragraph{Inertial measurement.} \Cref{tab:imu-noise-assumed} reports the noise
measured from the recorded stream and queries it, because no recording contains
a stationary interval long enough for a sound estimate: the longest is
\SI{2.16}{\second}. That query can be closed without a new recording, because
the noise is \emph{declared} in the robot model rather than emergent, so the
simulator's own configuration is the ground truth the measurement was trying to
recover.

\Cref{tab:injected-noise} collects what the simulator actually injects, together
with the measured values and the EuRoC reference. The measured gyroscope range
brackets the declared value, which corroborates both. The measured accelerometer
range does not: it is four to six times the declared figure, and that
discrepancy is the estimator's rather than the sensor's, because the residual on
the driving axis carries real longitudinal acceleration that a window of two
seconds cannot separate from noise. Prefer the declared values wherever a number
is needed.

Two readings follow. The simulated IMU is \emph{twice as noisy} as the EuRoC
reference on both channels, so it is not an optimistic sensor. The camera, at
about \num{1.3} grey levels out of \num{255} and with no distortion terms, is
much cleaner than any real one. Both bias correlation times exceed the
\SIrange{80}{125}{\second} length of the four shorter recordings, so within a
run the bias behaves as a slowly varying constant and its instability is never
exercised; only the two mapping runs, at \SIrange{288}{315}{\second}, approach
the accelerometer's \SI{300}{\second} correlation time.

Three further effects are absent: chassis vibration, which on a real platform is
frequently the dominant error; scale-factor, cross-axis and $g$-sensitivity
errors; and temperature drift. Finally, the message's \repo{orientation} field
carries no noise block at all and is therefore ground truth; no estimator in
this project consumes it, and none should
(\cref{sec:proprio-method}).

\paragraph{Wheel encoders.} \repo{JointStatePublisher} reports the true solver
angle. Slip consequently appears as a \emph{discrepancy} rather than an error:
the joint angle stays true, so encoder-integrated distance over-reads whenever
traction breaks, which is exactly a real encoder's behaviour. What is idealised
is resolution. A physical 1024\,CPR encoder quantises to \SI{6.1e-3}{\radian},
setting a floor on low-speed velocity estimation that the simulation does not
have. \repo{script/encoder_sim.py} exists to impose that floor downstream and
has not been applied to any result in this report.

\paragraph{Physics engine and solver.} \Cref{tab:physics-setup} records the
simulation's physics configuration, which is identical across all 28 world
files. Two entries deserve comment because they are easy to misread.

The \repo{<physics>} element declares \repo{type="ignored"}. That is not a
misconfiguration: in Gazebo Fortress the engine is selected by the physics system
plugin, not by that attribute, and the attribute is disregarded. No world passes
an \repo{<engine>} parameter to the plugin, so the engine is Fortress's default,
\repo{dartsim}. This matters for the friction discussion below, and it is the
reason \repo{slip1} and \repo{slip2} have no effect.

No solver block is declared anywhere: no iteration count, no SOR parameter, no
constraint-force mixing or error-reduction terms. Every one of those therefore
takes the engine default. A \SI{1}{\milli\second} step is a fine integration
step for a \SI{1.5}{\metre\per\second} ground vehicle, but the untuned contact
solver is the part of this setup least able to support a quantitative claim about
contact behaviour.

\paragraph{What the real recordings carry, and what they do not.} The real rig
publishes no wheel odometry in metric units and no joint states. In place of
them each bag carries \repo{/feedback/velocity} and \repo{/feedback/steering}
at \SI{50}{\hertz} as \texttt{std\_msgs/Float64}: the velocity is in a firmware

takes two values on every recording, so it carries no steering angle. The
consequence for the non-visual baseline is worked out in
\cref{sec:proprio-method}. The inertial stream is a WitMotion HWT101CT at
\SI{200}{\hertz} on the inherited topic name \repo{/hwt101ct_yaw_publisher};

\paragraph{Ground truth and clocks.} The simulation recordings carry

\repo{realv6} export runs at \SI{1.7}{\hertz} and fails them, which is why its

\subsection{Test site and experimental variables}
\label{sec:real-site}

\textbf{Spatial layout.} The test area is divided into two operating zones,
Zone~A and Zone~B, separated by and connected through a walkway (each zone
about \SI{3}{\metre} square, walkway \SI{1.25}{\metre} wide;
\cref{fig:test-field}). The division reproduces the traffic pattern of a
warehouse AMR that shuttles continuously between a pick-up and a drop-off
point. The robot's linear speed is limited to $v_{\max} =
\SI{1.5}{\metre\per\second}$ throughout.

\textbf{Ground truth by motion capture.} Evaluating SLAM error (ATE and RPE)
needs a reference accurate to millimetres. A motion-capture camera system is
installed around the test area and tracks reflective markers placed at the
robot's centre of mass at a rate above \SI{100}{\hertz}.

\textbf{Coordinate-frame alignment.} The SLAM pose $P_{\mathrm{slam}}$ is
expressed in the local odometry frame fixed at start-up, whereas the
motion-capture pose $P_{\mathrm{gt}}$ is expressed in the room's global frame.
Before errors are computed the two trajectories are aligned by a rigid-body
transformation; the alignment actually used for every result in this report,
and its treatment of scale, is defined in \cref{sec:method-trajectory}.

\textbf{Dynamic-environment variable.} Each time the robot completes a zone
transfer (for example arrives in Zone~B from Zone~A), the operator randomly
re-positions and re-counts the stacks of goods in the opposite zone before the
robot returns. This forces the SLAM system to face a scene that no longer
matches its map (map obsolescence), to test whether ORB-SLAM3's Atlas or
RTAB-Map's memory management can resolve the conflicting spatial evidence
without tracking loss.

\textbf{Illumination variable.} Data are collected along the same route at
three times of day representing different light levels and directions:
morning (08:00), oblique natural light casting shadows across the test area;
midday (12:00), maximum brightness, with possible high contrast or
over-exposure in places; and evening (18:00), low light relying mainly on the
building's artificial lighting, with raised image noise. The variable tests
both the camera hardware (Sony IMX390 HDR) and the robustness of the two SLAM
frameworks in keeping enough inlier features for odometry under variable light.

\textbf{Real-dataset status.} The four real recordings in use are listed in
\cref{tab:dataset-registry}: \repo{dataset_realv6_000} and
\repo{dataset_realv7_000} to \repo{_002}, each with inertial data at
\SI{200}{\hertz} and a planar optical-tracker reference
(\cref{sec:exp3-real}). Varied illumination is still absent, so the
illumination variable of this section is unexercised, and the real slots of
Experiments~2 and~4 remain planned for want of annotated frames and a surveyed
reference grid.

\section{The Four Experiments}
\label{sec:experiments}

Each experiment below is defined by its objective, its process, its evaluation
metrics, its constraints and the validity rule that decides whether a run
counts. Each is run in both domains; \cref{chap:results} reports each domain in
its own slot.

\subsection{Experiment 1: Non-visual baseline and estimator comparison}
\label{sec:proprio-method}

\textbf{Objective.} Establish a dead-reckoning baseline to determine whether the
visual pipelines (ORB-SLAM3 and VINS-Fusion) genuinely outperform the robot's
own wheel odometry, its IMU, and a wheel-plus-IMU extended Kalman filter, and
whether the uncertainty each estimator reports describes the error it makes.

\textbf{Process.} Wheel odometry, IMU dead reckoning and the EKF are run
offline on the same recordings the visual estimators consumed, from
proprioceptive topics only. A calibration pass measures each sensor's noise and
scale against ground truth first; the estimators then run and are scored on the
same interval as the visual runs.

\textbf{Evaluation metrics.} Aligned and anchored ATE, final drift as a fraction
of distance, final heading error, RPE at \SI{1}{\second}, and the covariance
consistency measures NEES and $k\sigma$ coverage.

\textbf{Validity rule.} A run counts only if the planar assumption holds
(maximum tilt below \SI{1}{\degree}), the IMU orientation field is not consumed,
and the number of wheel corrections equals the number of wheel-odometry
messages.

Three non-visual estimators are implemented in
\repo{script/proprio_estimator.py} to supply the dead-reckoning floor: wheel
odometry, IMU dead reckoning, and an extended Kalman filter fusing the two.
They consume only proprioceptive topics and no images.

\subsubsection{Implementation form and why it is offline}

All three read the recorded bag directly and are deterministic functions of it.
Run as live ROS nodes they would instead depend on replay rate, QoS delivery and
CPU contention, none of which is a property of the estimator being compared. The
cost is a stated asymmetry: the visual figures they are compared against were
produced by live runs, so any timing-induced error is present on one side of the
comparison only.

carries a non-zero orientation, angular-velocity or linear-acceleration
covariance. Gazebo Fortress does not populate them and
\texttt{AckermannSteering} exposes no noise parameter, so the noise model is
measured rather than read, by a \repo{calibrate} pass that writes
\repo{sensor_noise.yaml} per recording. \Cref{tab:proprio-noise} gives the

\SIrange{0.059}{0.077}{\radian\per\second}, because the track and the wheel base
are both \SI{0.42}{\metre} and a solid rear axle slips through every turn. The
bicycle model is selected automatically and was chosen on all four.

\subsubsection{The orientation field must not be used}

\texttt{sensor\_msgs/Imu.orientation} in these bags is not an estimate. Measured
over \repo{dataset_allsensor_realistic_000} it equals ground-truth yaw plus
exactly \SI{90}{\degree}, with a residual standard deviation of
\SI{0.001}{\degree} and no drift at all across \SI{125.6}{\second}: the plugin
publishes the true orientation from the simulator's entity-component manager.
Consuming it would give a dead-reckoning estimator a perfect attitude reference
that no real IMU has, and its output would measure ground truth. All three
estimators therefore integrate \texttt{angular\_velocity.z} instead, which
drifts honestly, by \SI{3.66}{\degree} over the same recording. Each run records
\repo{imu_orientation_used=NO} in its metadata so the exclusion is auditable.

\paragraph{Which noise model the baseline runs on.} By the design decision of
6 November 2026 the EKF reported as the baseline does \emph{not} use the
measured inertial noise of \cref{tab:proprio-noise}. Its three inertial terms
are the values both visual configurations declare, gyroscope density
\num{0.002}, accelerometer density \num{0.02} and gyroscope bias walk
\num{1e-4}, converted to a per-sample $\sigma$ at \SI{200}{\hertz} by
\repo{script/make_vslam_noise_yaml.py}. The reason is that the proprioceptive
and visual families must run on the same hand-set inertial model before their
accuracies can be compared at all; the configured gyroscope density is five to
seven times the measured one, and a filter given the measured value would be
competing against visual systems that were not. The measured-noise filter is
run beside it as a diagnostic row. Biases and both wheel $\sigma$ have no visual
counterpart and stay measured in both.

\subsubsection{EKF formulation}
\label{sec:ekf-formulation}

\paragraph{State and inputs.} The filter carries five planar states,
\begin{equation}
  \mathbf{x} = \begin{bmatrix}p_x & p_y & \theta & v & b_\omega\end{bmatrix}^{\top},
  \label{eq:ekf-state}
\end{equation}
where $b_\omega$ is the gyroscope $z$ bias. Roll and pitch stay within
\SI{0.002}{\degree} across every recording, so a full 15-state inertial
formulation would spend nine states on quantities this platform does not have,
and their covariances would be unobservable noise in the consistency test that
motivates the experiment.

The IMU is not a measurement here: it drives the prediction. Bias-corrected yaw
rate and longitudinal acceleration act as the input,
\begin{equation}
  \omega = \omega_{\text{gyro}} - b_\omega, \qquad a = a_x - b_a,
  \label{eq:ekf-input}
\end{equation}
with $b_a$ a constant measured during calibration rather than a tracked state.
Propagation uses the midpoint heading $\theta_m = \theta + \tfrac{1}{2}\omega\,\Delta t$,
which matters over the \SIrange{103}{171}{\metre} these recordings cover:
\begin{align}
  p_x &\mathrel{+}= v\cos\theta_m\,\Delta t + \tfrac{1}{2}a\cos\theta_m\,\Delta t^2, \notag\\
  p_y &\mathrel{+}= v\sin\theta_m\,\Delta t + \tfrac{1}{2}a\sin\theta_m\,\Delta t^2, \notag\\
  v   &\mathrel{+}= a\,\Delta t, \qquad \theta \mathrel{+}= \omega\,\Delta t.
  \label{eq:ekf-propagate}
\end{align}

\paragraph{Covariance and process noise.} With $\mathbf{F}=\partial f/\partial
\mathbf{x}$ and $\mathbf{G}$ mapping the noise inputs into the state,
\begin{equation}
  \mathbf{P} \leftarrow \mathbf{F}\mathbf{P}\mathbf{F}^{\top}
    + \mathbf{G}\,\mathrm{diag}(\sigma_a^2,\ \sigma_g^2,\ \sigma_{b}^2)\,\mathbf{G}^{\top}.
  \label{eq:ekf-predict}
\end{equation}
The non-trivial entries are
$F_{13}=-v\sin\theta_m\Delta t$, $F_{14}=\cos\theta_m\Delta t$,
$F_{23}=v\cos\theta_m\Delta t$, $F_{24}=\sin\theta_m\Delta t$ and
$F_{35}=-\Delta t$; the last couples bias error directly into heading, which is
what makes $b_\omega$ worth estimating. In $\mathbf{G}$, accelerometer noise
enters position as $\tfrac{1}{2}\cos\theta_m\Delta t^2$ and speed as $\Delta t$,
gyroscope noise enters heading as $\Delta t$, and the bias row carries
$\sqrt{\Delta t}$ rather than $\Delta t$ because a random walk accumulates as
$\sqrt{t}$.

Both IMU noise terms are therefore \emph{process} noise. Nothing from the IMU
appears in $\mathbf{R}$, because the IMU propagates the state rather than
observing it.

\paragraph{Measurement.} The wheels correct at \SI{50}{\hertz} with
\begin{equation}
  \mathbf{z} = \begin{bmatrix}v_{\text{wheel}} \\
    \omega_{\text{gyro}} - \omega_{\text{wheel}}\end{bmatrix}, \qquad
  \mathbf{H} = \begin{bmatrix}0&0&0&1&0\\ 0&0&0&0&1\end{bmatrix}, \qquad
  \mathbf{R} = \mathrm{diag}\!\left(\sigma_{v,w}^2,\ \sigma_{\omega,w}^2+\sigma_g^2\right).
  \label{eq:ekf-update}
\end{equation}
The second variance is a sum because that observation is a \emph{difference} of
two noisy sensors and inherits both. The update uses the Joseph form,
\begin{equation}
  \mathbf{P} \leftarrow (\mathbf{I}-\mathbf{K}\mathbf{H})\mathbf{P}
    (\mathbf{I}-\mathbf{K}\mathbf{H})^{\top} + \mathbf{K}\mathbf{R}\mathbf{K}^{\top},
  \label{eq:ekf-joseph}
\end{equation}
symmetrised afterwards. The shorter $(\mathbf{I}-\mathbf{K}\mathbf{H})\mathbf{P}$
does not reliably stay positive definite across the thousands of updates in a
run, and here the covariance is itself the measurement under test, so it cannot
be allowed to decay.

\paragraph{Where the numbers come from.} $\sigma_{v,w}$ and
$\sigma_{\omega,w}$ come from the wheel stream against ground truth
(\cref{tab:proprio-noise}); $\sigma_a$ and $\sigma_g$ come from the visual
configuration, as explained above. \moved{$\sigma_b$, the bias random walk, is
assumed rather than measured: the longest stationary window in any recording is
\SI{2.16}{\second} and an Allan-variance estimate needs minutes.}

\subsubsection{Why the bias, and not the heading, is observed}

The EKF's second measurement is deliberately an observation of the \emph{gyroscope
bias} and not of heading. Integrating the wheel yaw rate into a heading and
correcting $\theta$ with it would reproduce the wheel estimator inside the filter
and inherit its unbounded drift. Treating the instantaneous rate difference as an
observation of $b_\omega$ keeps each sensor supplying what it measures well: the
wheels know rate, the gyroscope knows change, and neither knows absolute heading,
so heading remains unobservable and its variance correctly continues to grow.

Measured scale errors are recorded but never divided out. Correcting them would
mean calibrating the estimator with the ground truth it is about to be scored
against; the scale error is a real property of encoder odometry and is retained.

\subsubsection{The real robot: a different baseline}

None of the three estimators above can be run on the real recordings. The rig
publishes no wheel odometry in metric units and no joint states, so there is no
wheel speed to integrate and no steering angle to put through the bicycle model;
the wheelbase, \SI{0.60}{\metre}, is known but has nothing to multiply. What the
bags do carry is a firmware-unit speed feedback and a gyroscope
(\cref{sec:dataset-registry}), which support one estimator:
\begin{equation}
  \theta(t) = \theta_0 + \int (\omega - b)\,\mathrm{d}t, \qquad
  \begin{bmatrix}p_x\\p_y\end{bmatrix} \mathrel{+}=
  k\,v_{\text{fb}} \begin{bmatrix}\cos\theta\\ \sin\theta\end{bmatrix} \Delta t,
  \label{eq:real-deadreckon}
\end{equation}
with $b$ the gyroscope bias measured over the stationary head of each recording
and $k$ the unknown speed scale. \repo{script/real_wheel_baseline.py} fits $k$,
the gyroscope axis and its sign on one recording by minimising the planar ATE
after rigid $SE(2)$ alignment, then holds all three on the others: the fit
recording's score is a calibration and only the held recordings are results.
Because no yaw-rate observation exists, there is no bias state to correct and
the EKF of \cref{eq:ekf-update} degenerates to this integration, so no filter
row is reported in the real domain.

\begin{queried}[One tuned constant]
The real baseline has a parameter fitted against the same tracker it is scored
on, albeit on a different recording. A measured scale, from the wheel
circumference and the gear ratio or from a tape-measured straight run, would
remove the objection; until then the real-domain comparison between this
baseline and the visual pipelines is weaker than its simulated counterpart.
\end{queried}

\subsection{Experiment 2: Offline YOLO detector performance}
\label{sec:yolo-eval-method}

\textbf{Objective.} Measure standalone detector performance independent of
SLAM, so that later filtering results can be attributed: how reliably the
detector finds and names warehouse objects, and how much of the frame a mask
built from its boxes would remove.

\textbf{Process.} The detector is run on every left-camera frame of the four
realistic recordings; ground-truth boxes are constructed by projecting the
collision mesh of every model the detector has a class for into the camera from
the simulator's pose stream; predictions are matched by class at an IoU
threshold; localisation and class assignment are scored separately. The
checkpoint is the four-class model
\repo{weight/runs_1/detect/train/weights/best.pt}, whose classes are bin, box,
bucket and forklift; the fourth fires on the pallet jacks, which are the moving
objects of the dynamic recordings, so moving-object recall is measurable. The
walking people are simulator actors with neither a pose in the simulator's
stream nor a collision mesh, and they are outside the class set, so no
ground-truth box can be projected for them and they are scored on neither
side.

\textbf{Evaluation metrics.} Precision, recall, F1, recall on the moving
subset, image-area coverage, and conditional class precision, recall and F1.
Recall is reported on two bases, because the scorer exempts truth boxes under
twelve pixels or more than \SI{70}{\percent} covered by nearer geometry: over
the boxes the exemptions keep, which is the detector's task, and over every
projected box, which is what is physically in view.

\textbf{Validity rule.} Overlays are inspected before any aggregate is
accepted, because invalid pose stamps, mesh units or camera transforms produce
plausible but wrong boxes.

\subsection{Experiment 3: Visual-inertial odometry with dynamic-environment
filtering}
\label{sec:vio-filter-method}

\textbf{Objective.} Determine whether masking dynamic-object features improves
localization, measure the compute cost of doing so, and verify that tracking
survives the filtering and that the added detector cost does not push either
pipeline below the input frame rate.

\textbf{Process, simulation.} Accuracy and compute are measured on different
recordings, because they need different designs.

\emph{Accuracy} is measured on the four \repo{dataset_allsensor_realistic}
recordings, one run per cell. The factors are the estimator, the feature
extractor (CPU or GPU) and the loop closer (active or disabled), each replayed
at rate 1.0 from the bag with the node live, which is the deployment condition.
The loop-closer state is read from each run's own log rather than from its
name, because a run can be launched with the closer enabled and have it
disabled by configuration.

\emph{Latency and resources} are measured only on the two mapping recordings,
each configuration run three times, so that a mean and a spread exist. One run
per cell cannot support an uncertainty, and the accuracy recordings are too
short to separate a steady state from the initialisation transient.

A filtered treatment, when one exists, is paired with the baseline of the same
estimator, extractor and closer state, and the pair is admissible only when the
filter demonstrably acted (matched detections, non-zero mask coverage, removed
tracks), the two runs received the same input to within \SI{5}{\percent} in
image count and duration, and both ran on the same node binary. No filtered run
exists in the current dataset set, so no pair has yet been formed. The
collection protocol is given in \cref{sec:collection-validity}.

\textbf{Process, real robot (planned).} The online procedure has four steps.
\emph{Step~1, initialisation and time synchronisation:} power the NRU-51V, the
stereo cameras and the IMU; start the optical tracker and calibrate the room.
The tracker and the robot keep separate clocks and the recordings made so far
are aligned after the fact by cross-correlating the tracker's speed with the
wheel-speed feedback (\cref{sec:method-trajectory}); synchronising the two
clocks at record time, by PTP or Chrony, would remove that estimation step and
the uncertainty it carries. \emph{Step~2, execution and environment alteration:} drive from the origin
in Zone~A to the goal in Zone~B at a linear speed not above
\SI{1.5}{\metre\per\second} through the Nav2 package; on arrival, trigger the
dynamic variable by randomly re-placing the $k$ stacks in Zone~A; return, alter
Zone~B, and alternate for five minutes per test cycle to represent a
lifelong-mapping load. \emph{Step~3, data logging:} record with rosbag2 the
6-DoF SLAM pose, the motion-capture reference, the detector boxes with
confidences, and the whole-pipeline latency per frame. \emph{Step~4, iteration
over the experimental matrix:} repeat steps 1--3 for both pipelines under the
three illumination levels. The \texttt{.db3} bags are then trajectory-extracted
and timestamp-matched before evaluation.

\textbf{Evaluation metrics.} ATE and rotational RMSE after rigid alignment,
RPE at $\Delta = \SI{1}{\second}$ (all pairs and jump-free), tracking-loss and
reset events, retained input fraction, throughput, process CPU and peak memory,
and per-module latency against the inter-frame budget.

\textbf{Validity rule.} A trajectory containing steps that imply more than
\SI{10}{\metre\per\second} is not read as ordinary drift; an indoor error above
\SI{50}{\metre} is divergence. A comparison across treatments is admissible only
for input-matched pairs with an active filter. A timing comparison between two
configurations is admissible only when their runs are interleaved from a cool
start, because the laptop throttles at \SI{90}{\celsius} and a block of
consecutive runs in one configuration confounds the configuration with the
thermal state.

\subsection{Experiment 4: Dense map reconstruction and map-quality evaluation}
\label{sec:map-eval-method}

\textbf{Objective.} Verify whether the reconstructed map accurately reflects the
physical environment and is usable by a route planner.

\textbf{Process.} RTAB-Map builds a database from a mapping run; the occupancy
grid is seated in the world by a fixed transform measured from the map alone;
geometry is scored against the world's collision meshes; drivability is scored
by stamping the true robot footprint along a ground-truth route that did not
build the map.

\textbf{Evaluation metrics.} Occupied-cell precision, recall over observed
surfaces and over the whole building, false-obstacle rate under the footprint,
unmapped footprint poses, clearance statistics, and the graph's node and link
counts.

\textbf{Validity rule.} Placement must be established independently before any
metric is read, and a drivability figure computed against the run that built
the map is a self-consistency check, not a result.

RTAB-Map grids are placed in the Gazebo world using one fixed rigid
world-to-map transform measured by \repo{script/fit_map_pose.py}. It is
constant for a database; the live \texttt{map~$\rightarrow$~odom} drift
correction is not reused for map placement. On a warehouse of parallel aisles
the placement search has a rival \SI{180}{\degree} away that can score higher
than the true pose, so a fit is accepted only after its overlay is read, and
the tool takes a \repo{--yaw-near} hint for the basin the spawn implies.

\repo{script/validate_map.py} rasterises world collision geometry and evaluates
occupied cells at a stated tolerance. It reports occupied-cell precision,
whole-world and observed-region recall, false obstacles under the true
$0.83\times0.50$~m footprint, unmapped footprint poses, and clearance. Graph
evaluation records neighbour, global-closure, local-space, and gravity links.
Localisation additionally requires time to first fix, accepted and rejected
matches, database checksums before and after read-only operation, pose
continuity, and known-world bounds. Finite covariance or a localisation status
message alone does not establish correctness.

A database is always probed with a recording that did not build it, because the
build route is drivable on its own map by construction: the camera cleared the
cells the robot passed through, so a self-probe measures the route and not the
map. The five databases evaluated are \repo{map/map_tiny/map_tiny.db} against
\repo{small_warehouse/small_warehouse_static_tinymap.world}, and the four
realistic-warehouse databases, one per layout under each of two build
configurations, against the static twin of their layout and probed with
\repo{dataset_allsensor_realistic_000} and \repo{_001}
(\cref{sec:map-quality}). The tiny map's own independent probe recording is
lost, so its drivability figure cannot be regenerated.
